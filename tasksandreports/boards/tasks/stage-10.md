# Agile-доски, этап 10: участники и новая форма доски

Работа — прямо в `main` (см. `tasksandreports/README.md`).

## Зачем
Замечания владельца после первой проверки на рабочем месте:
- форма «Новая доска» перегружена;
- выбор участников не работает.

Причина второго: после этапа 9 участником может быть только сотрудник с
допуском, то есть администратор, а себя форма не предлагает — список пустой.

Решение владельца: **участником доски может быть любой сотрудник.** Раздел
по-прежнему создают и видят целиком только администраторы. Участник без роли
допуска видит «Доски» в меню, но только доски, где он участник, и работает с
их карточками.

Прочитай `plan.md` (решения 11–12), `reviews/stage-09.md`, `feedback/2026-10-06/`
(фото формы), раздел досок в
`AGENTS.md`.

## 1. Права (`boards/permissions.py`)
`BOARD_ACCESS_ROLES` остаётся (сейчас `{ADMIN}`). Теперь это **полный
доступ**: все доски видны, создание по `BOARD_CREATOR_ROLES`, управление — как
раньше. Добавляется чтение по участию:

- `can_view_board(user, board)`:
  - полный доступ (`has_full_board_access(user)`: роль допуска или
    настоящий суперпользователь);
  - **или** активный сотрудник, который состоит в этой доске.

  Архивная доска читается так же.
- `can_use_boards(user)` — показывать ли раздел: полный доступ или участие
  хотя бы в одной доске (активный сотрудник). Один запрос `EXISTS`; результат
  кешируется на объекте пользователя на время запроса, как роли в
  `accounts.roles`. Он стоит в меню и контекст-процессоре на каждой странице.
- `readable_boards_q(user)` (или функция, возвращающая queryset id) — то же
  правило как фильтр. Ею пользуются:
  - список досок;
  - задачи (п. 3);
  - реальное время (п. 4).
- Право работать с доской, управлять ею, отменять карточки, писать сообщения
  начинается с `can_view_board(user, board)`, а не с `can_use_boards`.
  Остальная логика не меняется:
  - работать с карточками может участник или администратор;
  - управлять — владелец или администратор.
- `can_create_board` не меняется: полный доступ и `BOARD_CREATOR_ROLES`.
- Участник и исполнитель — **любой активный сотрудник**. Убери
  `board_access_q()` из `_active_users()`, `_clean_assignees()` и списков
  кандидатов. Если `board_access_q()` больше нигде не нужен, удали его.

## 2. Форма «Новая доска» и «Участники»
- Поля формы: **Название** и **Участники**. Больше ничего.
- **Участники** — повторяющиеся строки «Подразделение | Сотрудник», ровно как
  участники в редакторе протокола (`[data-employee-pair]`):
  - «+ Добавить участника» добавляет строку, «×» её удаляет;
  - подразделение только фильтрует список сотрудников, не хранится и не
    проверяется;
  - без JavaScript в каждой строке полный список активных сотрудников, и
    форма работает;
  - повторы схлопываются;
  - создатель всегда владелец и участник, в строках его нет.
- Страница «Участники» добавляет людей тем же виджетом.
- **Одна реализация виджета.** Логика пары сейчас живёт в
  `protocol_editor.js` (`syncPair()` и соседние функции).
  - Вынеси её в общий `static/js/employee_picker.js`: делегированные
    слушатели, никаких правил.
  - Протокол подключает его; его поведение не меняется, включая
    предупреждение `[data-pair-warning]` и правило «никогда не очищать
    выбранного».
  - Справочник «подразделения + сотрудники» строит одна функция. Перенеси
    `protocols.selectors.get_editor_directory()` в `accounts` (например,
    `accounts/directory.py`) и пусть протоколы её вызывают. Второй копии нет.
- `Board.description` остаётся в модели, но в форме его нет — новые доски
  получают пустое описание.
- **Подразделение доски убирается.**
  - Миграция: `Board.department` — `null=True, blank=True`. Существующие
    значения сохраняются; где оно пустое, на страницах ничего не выводится.
  - Новая карточка создаёт задачу **без подразделения**: доска — общая
    работа сотрудников разных отделов, как ошибка (`BUG`).
  - Миграция `tasks`: ветка `BOARD` в `task_source_relations_match_source_type`
    — `department` свободно (как у документных задач). Синхронно правь
    `Task.clean()`.
  - Существующие задачи не трогать.
  - Реестр «Задачи» и Excel показывают у такой задачи «—» — проверь.

## 3. Задачи `BOARD`
`tasks.permissions._without_boards_unless_allowed()`:
- полный доступ — все задачи `BOARD`;
- иначе — только задачи `BOARD` досок, которые пользователь читает.

Фильтр — `~Q(source_type=BOARD) | Q(board_card__board_id__in=<подзапрос id
читаемых досок>)`, без дублей строк. `can_view_task()` — через
`can_view_board()`.

## 4. Реальное время
- `board_targets(board)` — активные учётные записи с полным доступом плюс
  активные участники **этой** доски.
- Ревизия `boards`:
  - с полным доступом — как сейчас;
  - для участника — агрегаты только по его доскам;
  - без досок — постоянный токен.

## 7. Тесты
- Права:
  - участник-ОТК читает свою доску и работает на ней;
  - чужую доску не видит (403);
  - в меню «Доски» есть;
  - сотрудник без досок меню не видит;
  - неактивный участник ничего не получает;
  - администратор видит всё.
- Задачи:
  - участник видит задачи своей доски во «Все» и «Мои»;
  - задачи чужой доски не видит, `tasks:detail` — 404;
  - запросов не больше, чем было, плюс постоянная величина.
- Форма:
  - создание только с названием;
  - создание с участниками из разных подразделений;
  - повторы;
  - создатель не дублируется;
  - присланный неактивный пользователь отклоняется;
  - без JS (сырой POST) работает.
- Задача новой карточки — без подразделения; constraint принимает и NULL, и
  старое значение.
- Протоколы: все существующие тесты редактора зелёные (общий виджет).
- Реальное время: адресаты `board_targets`, ревизия участника меняется только
  от его досок.
- Миграции: с нуля на SQLite и PostgreSQL, откат `boards` и `tasks` на шаг.
- `WidenedBoardAccess` и `test_access.py` поправь под новое правило, не
  ослабляя проверок.

Браузер (скриншоты, 1920×1080):
1. Администратор создаёт доску с двумя участниками из разных подразделений.
2. Участник-ОТК входит: в меню «Доски», видна только эта доска, задача
   карточки есть в «Моих задачах».
3. Сотрудник без досок — пункта меню нет.
4. Протокол: выбор участника работает как прежде.
