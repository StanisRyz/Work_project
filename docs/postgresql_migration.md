# Перенос данных из SQLite в PostgreSQL

Инструкция описывает подготовленный, воспроизводимый механизм переноса.
**Сам рабочий перенос этой инструкцией не выполняется** — она описывает
порядок действий. Полная репетиция на копиях автоматизирована отдельным
скриптом: [Репетиция переноса SQLite → PostgreSQL](postgresql_rehearsal.md).
Production-переезд выполняется отдельным этапом с согласованным окном простоя.

Все команды находятся в приложении `maintenance` и ничего не удаляют
самостоятельно, кроме `prepare_empty_migration_target` — она удаляет строго
перечисленные строки справочников и только по явному подтверждению.

## 0. Подготовка копий

Экспорт выполняется **из остановленной копии базы и из копии media**, а не из
рабочих файлов: иначе можно получить частично записанные данные и файлы,
изменившиеся во время экспорта.

1. Остановите приложение (`runserver`, WSGI-процесс, планировщики очереди email).
2. Скопируйте базу и медиа:

```powershell
Copy-Item db.sqlite3 transfer\db-copy.sqlite3
Copy-Item -Recurse media transfer\media-copy
```

3. Убедитесь, что копии больше никем не изменяются.

## 1. Проверка источника (source preflight)

```powershell
$env:DATABASE_ENGINE = "sqlite"
$env:SQLITE_DB_PATH = "transfer\db-copy.sqlite3"

python manage.py check_migration_source --source-media-root transfer\media-copy
```

Команда работает только на SQLite, ничего не изменяет и проверяет:

- файл базы существует, доступен для чтения, и это **отдельная копия**, а не
  рабочий `db.sqlite3`;
- backend действительно SQLite;
- нет неприменённых миграций;
- `PRAGMA integrity_check` возвращает `ok`;
- соблюдены ключевые реляционные инварианты;
- стандартные номера актов уникальны;
- нет отстающих `ActNumberSequence`;
- все пути `ActAttachment` безопасны;
- каждый файл вложения присутствует в выбранном source media;
- фактический размер файла совпадает с `ActAttachment.file_size`, если оно
  заполнено;
- зафиксировано количество моделей, записей и вложений.

Запуск на рабочем `db.sqlite3` требует явного `--allow-default-database`. Без
этого флага команда отказывается работать и рекомендует сначала сделать
остановленную копию; с флагом использование рабочего файла остаётся
предупреждением в отчёте.

`--json-report <path>` сохраняет структурированный результат.

## 2. Экспорт миграционного пакета

`SQLITE_DB_PATH` указывает копию базы, `--source-media-root` — копию media:

```powershell
python manage.py export_migration_bundle `
  --output transfer\bundle `
  --source-media-root transfer\media-copy
```

Без `--source-media-root` используется `settings.MEDIA_ROOT`. Указанный путь
нормализуется и проверяется так же строго, как остальные файловые пути: он
должен существовать, быть каталогом и читаться. В `manifest.json` попадает
только безопасное описание источника (имя каталога, признак «каталог по
умолчанию», число файлов и суммарный объём) — абсолютный путь не раскрывается.

Команда откажется работать, если backend не SQLite, если есть непринятые
миграции, если каталог `--output` не пуст, если файл вложения отсутствует или
если путь вложения выходит за пределы выбранного каталога media. Пакет
собирается во временном каталоге и публикуется только после полного успеха,
поэтому частично сформированного пакета не остаётся.

### Отсутствующие вложения

`--allow-missing-media` остаётся **диагностической** возможностью:

```powershell
python manage.py export_migration_bundle --output transfer\bundle `
  --source-media-root transfer\media-copy --allow-missing-media
```

Пакет с непустым `missing_media` считается **неполным**:

- `manifest.complete` равен `false`, а список отсутствующих файлов сохраняется
  целиком;
- обычный `import_migration_bundle` такой пакет **отклоняет**;
- принять его можно только явным `--accept-missing-media`, который
  дополнительно требует подтверждения текстом `ПРИНЯТЬ НЕПОЛНЫЙ ПЕРЕНОС` и
  печатает полный список отсутствующих файлов;
- `verify_migration_bundle` всегда считает `missing_media` расхождением, если
  не задан специальный режим `--allow-missing-media`;
- статус неполного переноса попадает и в JSON-, и в Markdown-отчёт репетиции и
  блокирует production-переезд.

### Структура пакета

```
transfer/bundle/
  manifest.json              версия формата, дата, vendor, версии Python/Django,
                             состояние миграций, SHA-256 data.json, по каждой
                             модели — количество/максимальный PK/хеш, порядок
                             моделей, безопасное описание source media, список и
                             контрольные суммы media, исключённые модели,
                             признак полноты, предупреждения и отсутствующие файлы
  data.json                  детерминированная сериализация всех переносимых моделей
  media/                     файлы, на которые ссылаются записи ActAttachment
  verification-report.json   опционально, создаётся командой сверки
```

## 3. Повторная проверка пакета

```powershell
python manage.py verify_migration_bundle --input transfer\bundle --validate-only
```

Проверка не обращается к данным целевой базы и является полностью
самодостаточной. Она:

- требует `source_vendor == "sqlite"`;
- требует точного совпадения `model_order` с текущим `TRANSFERABLE_MODELS` и
  отклоняет повторяющиеся или неизвестные модели;
- пересчитывает **из `data.json`** количество, максимальный PK и
  детерминированный хеш отдельно по каждой модели и сравнивает их с manifest;
- проверяет, что каждая запись `data.json` относится к разрешённой модели;
- проверяет структуру блоков `migration_state`, `media_files` и `missing_media`
  (типы, безопасность путей, отсутствие дубликатов, формат контрольных сумм);
- проверяет SHA-256 `data.json` и каждого файла media по пути, размеру и хешу.

Manifest не может подтвердить сам себя: любое расхождение между заявленным и
пересчитанным даёт понятную ошибку `TransferError`.

## 4. Подготовка пустой PostgreSQL

Создайте базу и пользователя (см. `docs/postgresql_preparation.md`), затем:

```powershell
$env:DATABASE_ENGINE = "postgresql"
$env:DB_NAME = "quality_ecosystem"
$env:DB_USER = "quality_ecosystem"
$env:DB_PASSWORD = "..."
$env:EMAIL_NOTIFICATIONS_ENABLED = "false"

python manage.py migrate
```

Миграции данных сами создают строки в `references.ActStatus` (`ARCHIVED`,
`OTK_REVIEW`) и `references.TaskStatus` (`IN_PROGRESS`, `COMPLETED`). Пакет
содержит собственные копии этих строк, поэтому перед импортом их нужно убрать:

```powershell
python manage.py prepare_empty_migration_target
python manage.py prepare_empty_migration_target --execute --confirm "ОЧИСТИТЬ ТЕСТОВУЮ БАЗУ"
```

Команда разрешена только на PostgreSQL, по умолчанию работает как dry-run,
перед удалением требует и `--execute`, и точное текстовое подтверждение,
отказывается работать при обнаружении любых пользовательских данных, удаляет
только перечисленные выше коды, не использует `flush`, не удаляет
пользователей, акты, задачи, уведомления и файлы и печатает точный список
затрагиваемых таблиц и строк.

## 5. Проверка целевой базы (target preflight)

```powershell
python manage.py check_migration_target --previous-report transfer\rehearsal-report.json
```

Проверяется: backend — PostgreSQL; все миграции применены; email-уведомления
отключены; переносимые таблицы пусты; `MEDIA_ROOT` пуст или отсутствует; база
доступна для чтения и записи (пробная транзакция всегда откатывается);
у пользователя базы есть необходимые права; версия PostgreSQL доступна для
отчёта; по данным предыдущего rehearsal-отчёта нет незавершённого импорта.

`MEDIA_ROOT` можно направить на отдельный каталог переменной окружения
`MEDIA_ROOT_PATH` — это нужно, чтобы репетиция не писала в рабочий `media`.

## 6. Dry-run

```powershell
python manage.py import_migration_bundle --input transfer\bundle --dry-run
```

Dry-run не изменяет ни базу, ни файловую систему. Он повторяет полную проверку
пакета, проверяет применённые миграции, полноту пакета, пустоту переносимых
таблиц и доступность `MEDIA_ROOT`, после чего печатает список планируемых
действий.

## 7. Импорт

```powershell
python manage.py import_migration_bundle --input transfer\bundle --json-report transfer\import.json
```

Команда повторяет все проверки, готовит файлы во временном каталоге и внутри
**одной** `transaction.atomic()` выполняет три действия:

1. загрузку fixture штатными сериализаторами Django (без ручного SQL);
2. сброс последовательностей PostgreSQL;
3. синхронизацию `ActNumberSequence`.

Синхронизация счётчиков завершается **до commit**. Если сброс
последовательностей или синхронизация завершились ошибкой, все загруженные
строки откатываются и целевая база остаётся пустой.

Активация каталога media выполняется только после успешной фиксации
транзакции. Бизнес-уведомления и workflow-сервисы при загрузке не запускаются:
записи сохраняются в режиме `raw`.

Импорт отклоняется, если backend не PostgreSQL, если
`EMAIL_NOTIFICATIONS_ENABLED=true`, если не все миграции применены, если пакет
неполный (без `--accept-missing-media`), если переносимые таблицы не пусты или
если `MEDIA_ROOT` не пуст при наличии файлов в пакете.

### Частичный результат: media не активирована

Если база зафиксирована, а копирование файлов в `MEDIA_ROOT` не удалось,
команда **не** сообщает об обычном успехе. Она возвращает структурированный
результат со статусом `partial`, печатает точную инструкцию восстановления и
завершается ненулевым кодом:

1. не запускать приложение на этой базе — перенос не завершён;
2. скопировать файлы из `bundle/media` в `MEDIA_ROOT`, сохранив относительные
   пути;
3. повторно запустить `verify_migration_bundle --input transfer\bundle`;
4. повторный импорт в эту базу невозможен (таблицы уже не пусты) — если
   восстановить media не удаётся, очистить целевую базу и `MEDIA_ROOT` и
   повторить перенос с нуля.

## 8. Восстановление последовательностей

Выполняется внутри транзакции импорта: используются стандартные операции
backend (`connection.ops.sequence_reset_sql`), имена последовательностей нигде
не захардкожены. Обрабатываются все переносимые модели с
`AutoField`/`BigAutoField`. После этого новые записи получают PK, не
конфликтующие с импортированными.

Там же выполняется синхронизация `ActNumberSequence`: для каждого года
находится максимальный фактический номер формата `АОК-YYYY-NNN`, отсутствующий
счётчик создаётся, отстающий поднимается. Счётчик никогда не уменьшается,
нестандартные номера игнорируются, повторный запуск ничего не меняет.

## 9. Итоговая сверка

```powershell
python manage.py verify_migration_bundle --input transfer\bundle --report transfer\verification-report.json
```

Сверка сравнивает количество записей, максимальные PK и детерминированные хеши
по каждой модели, проверяет каждый файл media по пути, размеру и SHA-256,
проверяет `ActNumberSequence` и ключевые связи (профили, дефекты, история,
комментарии, вложения, мероприятия, исполнители, задачи, уведомления и
доставки, уникальность стандартных номеров). Непустой `missing_media` всегда
считается расхождением, если не задан `--allow-missing-media`. При любом
расхождении команда завершает работу ненулевым кодом и печатает список
различий.

## 10. Smoke-проверки

```powershell
python manage.py run_postgresql_smoke_checks --json-report transfer\smoke.json
```

Команда работает только на PostgreSQL и только после импорта. Read-only
проверки обходят реальные данные теми же запросами и permission-функциями,
что и views. Проверки записи выполняют полный сценарий (пользователь → акт →
дефект → комментарий → история → мероприятие → задача → уведомление →
завершение задачи → ограничения и связи) внутри транзакции с обязательным
откатом и затем убеждаются, что тестовые данные не сохранились. Email не
отправляется, `EMAIL_NOTIFICATIONS_ENABLED` должна оставаться `false`.

## 11. Действия при ошибке

- **Ошибка на проверке источника.** Пакет не собирается. Устраните замечания и
  повторите — база не изменена.
- **Ошибка на экспорте.** Пакет не публикуется; временный каталог удаляется.
- **Ошибка на проверке пакета или dry-run.** База не изменена. Пересоберите
  пакет из копии SQLite.
- **Ошибка внутри транзакции импорта.** Транзакция откатывается целиком,
  включая сброс последовательностей и синхронизацию `ActNumberSequence`; файлы
  media не активируются. База остаётся пустой — повторите импорт после
  устранения причины.
- **База импортирована, но активация media не удалась.** Команда сообщает о
  частичном результате и печатает инструкцию восстановления (см. раздел 7).
- **Сверка нашла расхождения.** Не переключайте приложение на PostgreSQL.
  Разберите список различий, пересоздайте целевую базу и повторите перенос с
  нуля.
- **Smoke-проверки не пройдены.** Целевая база непригодна; разберите
  отказавшие проверки до повторной репетиции.

## 12. Очистка чувствительных временных файлов

Пакет содержит реальные рабочие данные: пользователей, акты, вложения. После
завершения работ удалите копии, пакет и отчёты:

```powershell
Remove-Item -Recurse -Force transfer
```

Каталоги пакетов, копии SQLite и media, целевой media репетиции и отчёты
добавлены в `.gitignore` и не должны попадать в репозиторий.

## Что этот механизм не делает

- Не переносит рабочую базу автоматически.
- Не очищает целевую базу от пользовательских данных и не перезаписывает
  существующие файлы.
- Не устанавливает PostgreSQL и не настраивает веб-сервер.
- Не переключает production и не меняет бизнес-процесс.
- Не выполняет обратную миграцию PostgreSQL → SQLite и дельта-синхронизацию.
- Не шифрует пакет: защита каталога — задача операционной среды.
