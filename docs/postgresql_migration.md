# Перенос данных из SQLite в PostgreSQL

Инструкция описывает подготовленный, воспроизводимый механизм переноса.
**Сам рабочий перенос этой инструкцией не выполняется** — она описывает
репетицию и порядок действий. Полная репетиция на копии и production-переезд
выполняются отдельным этапом с согласованным окном простоя.

Все команды находятся в приложении `maintenance` и ничего не удаляют
самостоятельно.

## 0. Подготовка копий

Экспорт выполняется **из остановленной копии** базы, а не из работающего
файла: иначе можно получить частично записанные данные.

1. Остановите приложение (`runserver`, WSGI-процесс, планировщики очереди email).
2. Скопируйте базу и медиа:

```powershell
Copy-Item db.sqlite3 transfer\db-copy.sqlite3
Copy-Item -Recurse media transfer\media-copy
```

3. Убедитесь, что копия открывается только на чтение и её никто не изменяет.

## 1. Экспорт миграционного пакета

`SQLITE_DB_PATH` позволяет указать копию, не подменяя рабочий файл:

```powershell
$env:DATABASE_ENGINE = "sqlite"
$env:SQLITE_DB_PATH = "transfer\db-copy.sqlite3"

python manage.py export_migration_bundle --output transfer\bundle
```

Команда откажется работать, если backend не SQLite, если есть непринятые
миграции, если каталог `--output` не пуст, если файл вложения отсутствует или
если путь вложения выходит за пределы `MEDIA_ROOT`. Пакет собирается во
временном каталоге и публикуется только после полного успеха, поэтому
частично сформированного пакета не остаётся.

Если часть файлов вложений действительно утеряна и это осознанное решение:

```powershell
python manage.py export_migration_bundle --output transfer\bundle --allow-missing-media
```

Отсутствующие файлы будут перечислены в выводе и в `manifest.json`.

### Структура пакета

```
transfer/bundle/
  manifest.json              версия формата, дата, vendor, версии Python/Django,
                             состояние миграций, SHA-256 data.json, по каждой
                             модели — количество/максимальный PK/хеш, список и
                             контрольные суммы media, исключённые модели,
                             предупреждения и отсутствующие файлы
  data.json                  детерминированная сериализация всех переносимых моделей
  media/                     файлы, на которые ссылаются записи ActAttachment
  verification-report.json   опционально, создаётся командой сверки
```

## 2. Проверка manifest

Просмотрите `manifest.json` до импорта:

- `bundle_format_version` — должна поддерживаться текущим кодом;
- `models` — количество записей по каждой модели соответствует ожиданиям;
- `missing_media` — пусто (или ожидаемо пусто по договорённости);
- `migration_state.pending` — пусто.

## 3. Подготовка пустой PostgreSQL

Создайте базу и пользователя (см. `docs/postgresql_preparation.md`), затем:

```powershell
$env:DATABASE_ENGINE = "postgresql"
$env:DB_NAME = "quality_ecosystem"
$env:DB_USER = "quality_ecosystem"
$env:DB_PASSWORD = "..."
$env:EMAIL_NOTIFICATIONS_ENABLED = "false"

python manage.py migrate
```

**Важно.** Миграции данных сами создают строки в `references.ActStatus` и
`references.TaskStatus`. Пакет содержит собственные копии этих строк, поэтому
перед импортом их нужно удалить вручную — команда импорта принципиально ничего
не удаляет:

```sql
DELETE FROM references_actstatus;
DELETE FROM references_taskstatus;
```

После этого все переносимые таблицы должны быть пусты.

## 4. Dry-run

```powershell
python manage.py import_migration_bundle --input transfer\bundle --dry-run
```

Dry-run не изменяет ни базу, ни файловую систему. Он проверяет manifest,
контрольные суммы `data.json` и всех файлов media, применённые миграции,
пустоту переносимых таблиц и доступность `MEDIA_ROOT`, после чего печатает
полный список планируемых действий.

## 5. Импорт

```powershell
python manage.py import_migration_bundle --input transfer\bundle
```

Команда повторяет все проверки, готовит файлы во временном каталоге, загружает
данные штатными сериализаторами Django внутри одной транзакции (без ручного
SQL), восстанавливает последовательности и только после успешной фиксации базы
активирует каталог media. Бизнес-уведомления и workflow-сервисы при загрузке не
запускаются: записи сохраняются в режиме `raw`.

Импорт отклоняется, если backend не PostgreSQL, если `EMAIL_NOTIFICATIONS_ENABLED=true`,
если не все миграции применены, если переносимые таблицы не пусты или если
`MEDIA_ROOT` не пуст при наличии файлов в пакете.

## 6. Восстановление последовательностей

Выполняется автоматически в конце импорта: используются стандартные операции
backend (`connection.ops.sequence_reset_sql`), имена последовательностей нигде
не захардкожены. Обрабатываются все переносимые модели с `AutoField`/`BigAutoField`.
После этого новые записи получают PK, не конфликтующие с импортированными.

Там же выполняется синхронизация `ActNumberSequence`: для каждого года
находится максимальный фактический номер формата `АОК-YYYY-NNN`, отсутствующий
счётчик создаётся, отстающий поднимается. Счётчик никогда не уменьшается,
нестандартные номера игнорируются, повторный запуск ничего не меняет.

## 7. Итоговая сверка

```powershell
python manage.py verify_migration_bundle --input transfer\bundle --report transfer\verification-report.json
```

Сверка сравнивает количество записей, максимальные PK и детерминированные хеши
по каждой модели, проверяет каждый файл media по пути, размеру и SHA-256,
проверяет `ActNumberSequence` и ключевые связи (профили, дефекты, история,
комментарии, вложения, мероприятия, исполнители, задачи, уведомления и
доставки, уникальность стандартных номеров). При любом расхождении команда
завершает работу ненулевым кодом и печатает список различий.

## 8. Действия при ошибке

- **Ошибка на экспорте.** Пакет не публикуется; временный каталог удаляется.
  Устраните причину и повторите.
- **Ошибка на проверке пакета или dry-run.** База не изменена. Пересоберите
  пакет из копии SQLite.
- **Ошибка внутри транзакции импорта.** Транзакция откатывается целиком,
  файлы media не активируются. База остаётся пустой — повторите импорт после
  устранения причины.
- **База импортирована, но активация media не удалась.** Команда сообщает об
  этом явно. Скопируйте файлы из `bundle/media` в `MEDIA_ROOT` вручную и
  повторно запустите `verify_migration_bundle`.
- **Сверка нашла расхождения.** Не переключайте приложение на PostgreSQL.
  Разберите список различий, при необходимости очистите целевую базу
  вручную и повторите перенос с нуля.

## 9. Очистка чувствительных временных файлов

Пакет содержит реальные рабочие данные: пользователей, акты, вложения. После
завершения работ удалите копии и пакет:

```powershell
Remove-Item -Recurse -Force transfer
```

Каталоги пакетов, резервные копии SQLite и отчёты переноса добавлены в
`.gitignore` и не должны попадать в репозиторий.

## Что этот механизм не делает

- Не переносит рабочую базу автоматически.
- Не очищает целевую базу и не перезаписывает существующие файлы.
- Не устанавливает PostgreSQL и не настраивает веб-сервер.
- Не переключает production и не меняет бизнес-процесс.
- Не шифрует пакет: защита каталога — задача операционной среды.
