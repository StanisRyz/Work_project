# Real-time

Интерфейс обновляется без перезагрузки страницы: сервер публикует событие в
Redis Pub/Sub, браузер получает его через Server-Sent Events и **перезапрашивает**
нужный блок обычным авторизованным запросом.

Одно правило определяет всю подсистему:

> Событие говорит, **что** изменилось. Оно никогда не говорит, **каким** это
> стало. PostgreSQL и обычные endpoint'ы с проверкой прав остаются источником
> истины.

## 1. Контракт события

Событие — неизменяемая структура из `realtime/events.py` со строго
фиксированным набором полей на проводе:

```json
{
  "schema_version": 1,
  "event_id": "7f1c…",
  "event_type": "act.status_changed",
  "occurred_at": "2026-08-06T12:00:00+05:00",
  "resource_type": "act",
  "resource_id": 417,
  "data": {"from_status_code": "KO_REVIEW", "to_status_code": "TO_ANALYSIS", …}
}
```

Ограничения проверяются и при создании, и при разборе принятого сообщения:

- набор полей точный; лишнее поле — ошибка, а не игнорируемое значение. Это
  закрывает попытку подсунуть в событие target или имя канала;
- `data` содержит только JSON-скаляры, списки и словари: до 20 ключей и до 3
  уровней вложенности. Модель, `datetime`, `set` или `Decimal` отклоняются;
- `resource_type` — одно из `act`, `comment`, `notification`, `task`, `user`;
- размер сериализованного события ограничен `REALTIME_MAX_EVENT_BYTES`
  (по умолчанию 16 КБ) и проверяется дважды: перед публикацией и перед записью
  в поток;
- `schema_version` — только 1.

**Что в `data` не попадает никогда**: текст комментария, описание дефекта,
решение КО, корневая причина, текст задачи и результат выполнения, данные
заказчика и партии, email, имена файлов, права, хеши паролей, целые модели.

## 2. Типы событий

| Тип | Ресурс | Значимые поля `data` |
| --- | --- | --- |
| `notification.created` | `notification` | `recipient_id`, `actor_id`, `act_id`, `notification_event_type` |
| `notification.read` | `user` | `changed_count`, `unread_count`, `scope`, `notification_ids` (только для небольшой операции) |
| `task.created` | `task` | `act_id`, `source_action_id`, `status_code`, `assignee_count` |
| `task.updated` | `task` | `act_id`, `status_code`, `changed_fields` |
| `task.completed` | `task` | `act_id`, `status_code`, `completed_by_id` |
| `act.created` | `act` | `status_code`, `author_id` |
| `act.updated` | `act` | `status_code` |
| `act.status_changed` | `act` | `from_status_code`, `to_status_code`, `history_event_id`, `actor_id` |
| `comment.created` | `comment` | `act_id`, `author_id` |

Значения строк — часть контракта. Новый тип добавляется только в
`RealtimeEventType`; отдельный тип на каждый статус акта не заводится —
переходы описываются одним `act.status_changed`.

`notification.read` при `scope=all` сообщает только счётчики: отметка всей
истории прочитанной не должна порождать неограниченный список идентификаторов.

## 3. Явные эмиттеры

События публикуются **явными вызовами из сервисов**, никогда из `post_save`.
Сигнал сработал бы при загрузке фикстур, при техническом `save()` и до того,
как связанные объекты существуют (задача без исполнителей).

| Эмиттер | Где вызывается |
| --- | --- |
| `emit_act_created` | `acts.views.act_create`, внутри атомарного блока после сохранения акта и дефектов |
| `emit_act_status_changed` | `acts.services.add_act_history_event`, когда переход действительно сменил статус |
| `emit_act_updated` | там же, для события истории `ACT_EDITED` |
| `emit_comment_created` | `acts.services.add_act_comment` — ровно одно событие на созданный комментарий |
| `emit_task_created` | `acts.services.approve_act`, после сохранения задачи и всех её исполнителей |
| `emit_task_updated` | `tasks.services.replace_task_assignees` — при изменении состава исполнителей |
| `emit_task_completed` | `tasks.services.complete_task`, внутри блокировки |
| `emit_notification_created` | `notifications.services.create_notifications`, только для действительно созданной строки |
| `emit_notification_read` | `notifications.services.mark_notifications_read`, одно агрегированное событие на операцию |

Каждый эмиттер выходит **до** разрешения получателей, если real-time выключен:
конфигурация по умолчанию не выполняет ни одного лишнего запроса.

## 4. `publish_after_commit`

`publish_after_commit(event, targets)` нормализует targets внутри транзакции —
поэтому некорректный target падает на месте вызова, а не внутри commit-хука — и
регистрирует публикацию через `transaction.on_commit`. Откат транзакции не
публикует ничего.

Публикация происходит уже после фиксации бизнес-операции, поэтому отказ
транспорта не может её сломать. При `REALTIME_FAIL_SILENTLY=true` (по
умолчанию) ошибка записывается в logger `realtime` и подавляется; в логе
остаются идентификатор и тип события, ресурс, число targets, backend и класс
исключения — но никогда payload, имена каналов и Redis URL.

## 5. Targets и персональные каналы Redis

Target отвечает на вопрос «кому это можно отдать» и вычисляется **только на
сервере** из уже существующих правил маршрутизации уведомлений
(`get_act_participants`, `get_comment_participants`,
`get_recipients_for_history_event`). Второго набора правил `realtime` не
заводит. В публичном payload target не появляется никогда.

Существуют два вида: `user:<id>` — авторитетный адресат, и `act:<id>` —
дополнительная подсказка маршрутизации в контракте события.

Имя канала строится только из проверенного target: `<prefix>:<target.key>`,
где префикс задаётся `REALTIME_CHANNEL_PREFIX`. Функции, превращающей
произвольную строку в имя канала, в проекте нет.

**Redis-публикация идёт только в каналы, на которые клиент может подписаться, —
сегодня это `user:<id>`.** Запись в `act:<id>` создавала бы сообщения, которые
никто не может получить: подписка на «комнату акта» потребовала бы авторизации
через `acts.permissions.can_view_act`, и расширять список подписываемых видов
можно только вместе с такой авторизацией.

Publisher сериализует событие один раз и пишет все каналы одним
`pipeline(transaction=False)`: это независимые fire-and-forget команды
`PUBLISH`, атомарность им не нужна. Таймауты Redis по умолчанию около секунды,
потому что публикация выполняется внутри запроса пользователя; публикация
медленнее `REALTIME_REDIS_SLOW_PUBLISH_MS` пишется как `realtime.slow_publish`
с типом события, числом каналов и длительностью.

## 6. SSE endpoint

`GET /realtime/events/` — асинхронная вьюха, требующая ASGI.

- подписка строится **только** из `request.user`, полученного из сессии.
  Строка запроса, путь и тело запроса на неё не влияют;
- анонимный запрос — `401`;
- `REALTIME_ENABLED=false` — `204`, Redis при этом не трогается вовсе;
- недоступный Redis (preflight PING не прошёл) — `503`, а не зависшее
  соединение;
- первый кадр — `retry:` с `REALTIME_RECONNECT_DELAY_MS`;
- при молчании дольше `REALTIME_HEARTBEAT_SECONDS` (по умолчанию 25 с)
  отправляется SSE-комментарий, чтобы прокси и клиент отличали живое
  соединение от мёртвого;
- поток закрывается сам через `REALTIME_MAX_CONNECTION_SECONDS` (по умолчанию
  900 с), чтобы следующее соединение заново прошло аутентификацию и проверку
  прав;
- ответ помечен `Cache-Control: no-cache, no-store, no-transform`,
  `X-Accel-Buffering: no`, `Vary: Cookie`. Hop-by-hop заголовки не
  выставляются — ими владеет ASGI-сервер;
- некорректное, неизвестное или превышающее лимит сообщение **отбрасывается**:
  оно не доходит до клиента и не разрывает поток;
- при отключении освобождается всё: `asyncio.CancelledError` обрабатывается,
  выполняется unsubscribe, закрываются PubSub и клиент. Закрытая вкладка —
  событие уровня DEBUG, а не ошибка.

`GET /realtime/sync/` — вторая половина контракта, описана в разделе 8.

## 7. Клиент: EventSource и один лидер среди вкладок

Модули лежат в `static/js/realtime/`: `core.js` (EventSource, шина событий,
конечный автомат состояний), `tabs.js`, `sync.js` и функциональные модули
`notifications.js`, `tasks.js`, `acts.js`, плюс `start.js`. Ни фреймворка, ни
сборщика, ни сторонней зависимости.

`EventSource` создаётся **только** из серверной конфигурации в `base.html`. Он
не принимает ни идентификатор пользователя, ни target, ни имя канала. Если
real-time выключен или пользователь анонимен, конфигурация и скрипты не
рендерятся вовсе. До браузера доходят только обычные числа, обратные URL и
случайный непривилегированный epoch текущей Django-сессии: ни Redis URL, ни
пароль, ни session key, ни пространство имён серверных каналов.

**Одно соединение на аутентифицированную сессию, а не на вкладку.** При доступном
`BroadcastChannel` вкладка-лидер держит EventSource и восстановление, а
остальным пересылает нормализованные события и снимки сверки; они подают их в
ту же шину. Имя канала и ключ аренды в `localStorage` изолированы случайным
session epoch, который не является session key и не даёт серверных прав.
Аренда лидера живёт в `localStorage`
(`REALTIME_LEADER_LEASE_SECONDS`, обновление раз в
`REALTIME_LEADER_HEARTBEAT_SECONDS`). Кратковременные два лидера допустимы:
дедупликация по `event_id` не даёт показать второй toast.

Новая вкладка-последователь не ждёт следующего события: она запрашивает у
лидера снимок (`sync.request` / `sync.response`) и применяет его через тот же
путь сравнения ревизий. Если лидер не ответил за короткий таймаут, вкладка
выполняет ровно одну собственную сверку, но никогда не открывает второй
EventSource и не запускает постоянный polling. Сообщение `leader.state`
позволяет последователю показать индикатор degraded, не открывая поток.

Межвкладочные сообщения (`event`, `sync`, `sync.request`, `sync.response`,
`leader.state`) несут schema version и session epoch; чужая или устаревшая
сессия отбрасывается. Остальные данные — ровно те же, что сервер и так отдал бы
этой сессии.

Отсутствие `BroadcastChannel` или `localStorage` не отключает real-time: каждая
вкладка просто работает самостоятельно. Каждый модуль защищён
`core.claimModule(<name>)`, поэтому повторно подключённый скрипт не поднимает
второй набор таймеров и слушателей.

## 8. Фрагменты и сверка ревизий

**Событие — сигнал перезапросить, а не источник HTML.** Разметку рендерит
Django, клиент подставляет уже готовый фрагмент.

Фрагментные endpoint'ы:

| Блок | Endpoint | Ключ ревизии |
| --- | --- | --- |
| Колокольчик | `/notifications/header-fragment/` | `notifications` |
| Реестр задач | `/quality/tasks/list-fragment/` | `tasks` |
| Реестр актов | `/quality/acts/list-fragment/` | `acts` |
| Сводка акта | `/quality/acts/<pk>/live-summary-fragment/` | `acts` |
| Рабочая вкладка акта | `/quality/acts/<pk>/work-fragment/` | `acts` |
| История акта | `/quality/acts/<pk>/history-fragment/` | `comments` |
| Комментарии акта | `/quality/acts/<pk>/comments-fragment/` | `comments` |
| Связанные мероприятия | `/quality/acts/<pk>/activities-fragment/` | `activities` |

Каждый фрагмент заново загружает объект, заново проверяет `request.user` и
права, не принимает идентификатор пользователя, ничего не меняет на GET и
отдаётся с `Cache-Control: no-store, private`. Полная страница и фрагмент
собираются одним и тем же строителем состояния, поэтому обновлённый блок не
может разойтись с перезагрузкой.

`GET /realtime/sync/` возвращает непрозрачные токены ревизий и безопасные
счётчики:

```json
{
  "schema_version": 1,
  "generated_at": "…",
  "revisions": {"notifications": "…", "tasks": "…", "acts": "…",
                "comments": "…", "activities": "…"},
  "unread_notifications": 3
}
```

Токен — хеш агрегатов по строкам, которые пользователь **уже** может видеть,
через те же правила прав, что и страницы. Для актов и задач это глобальный
read-only набор авторизованного пользователя, для уведомлений — только его
собственные записи. Токен не содержит сериализованных строк или бизнес-текста.
Стоимость — фиксированное небольшое число агрегатных запросов: сверка не
загружает строки и не материализует идентификаторы в Python, поэтому не растёт
вместе с объёмом видимых данных.

Клиент сравнивает токены и обновляет только те блоки, чей токен сдвинулся.
Одинаковые токены не стоят ни одного запроса фрагмента.

## 9. Восстановление

**SSE — best-effort. Корректность возвращает `/realtime/sync/`.**

- **на каждом `open`**, включая любое переподключение браузера, выполняется
  сверка: пропущенное событие, перезапуск Redis или закрытый на час ноутбук не
  оставляют устаревшее состояние. Первый `open` не показывает toast'ы для уже
  существовавших уведомлений;
- **fallback polling** включается только в состоянии `degraded` (нет успешного
  `open` дольше `REALTIME_DEGRADED_AFTER_SECONDS`, по умолчанию 20 с) или когда
  `EventSource` отсутствует в браузере. Он опрашивает `/realtime/sync/` с
  интервалом `REALTIME_SYNC_POLL_SECONDS` для видимой вкладки и
  `REALTIME_SYNC_HIDDEN_POLL_SECONDS` для скрытой, добавляет джиттер, не
  выполняется при `navigator.onLine === false` и прекращается сразу после
  восстановления SSE;
- **live safety-sync** — редкая периодическая сверка, пока поток жив
  (`REALTIME_LIVE_SYNC_SECONDS`, по умолчанию 300 с, диапазон 60–1800 с). Она
  ловит событие, которое Redis опубликовал, но никто не доставил. Это не замена
  polling: fallback polling и safety-таймер взаимоисключающи;
- **восстановление имеет ровно одного владельца на аутентифицированную сессию.** Каждый
  периодический запрос к серверу разрешён только вкладке, владеющей
  восстановлением: лидеру при координации вкладок и каждой вкладке, когда
  координации нет. Иначе N вкладок умножили бы трафик восстановления на N;
- одновременно выполняется **не более одной** сверки; собственного цикла
  переподключения поверх `EventSource` нет;
- события дедуплицируются по `event_id` в ограниченном множестве, поэтому
  повторная доставка не даёт второй toast.

## 10. Истечение сессии

Технические endpoint'ы (`/realtime/sync/` и фрагментные) обёрнуты в
`realtime.auth.realtime_login_required`, а не в человеческий `login_required`:
анонимный или истёкший запрос получает компактный JSON `401`
(`{"error": "authentication_required"}`) с `Cache-Control: no-store, private`, а
не HTML-редирект на форму входа.

Клиент проверяет `response.redirected`, затем статус, затем `Content-Type` — и
только после этого вызывает `.json()`. Неожиданный HTML никогда не доходит до
парсера и до DOM.

Потеря аутентификации (401/403 или редирект, которого endpoint выдавать не
должен) переводит клиент в состояние `stopped`: EventSource закрывается,
polling и safety-таймер останавливаются, таймер рукопожатия сбрасывается,
незавершённые запросы отменяются. Бесконечного цикла переподключений и потока
технических ошибок пользователю не возникает.

`404` на фрагменте одного акта останавливает обновление **только** этого акта:
колокольчик, список задач и остальные акты продолжают обновляться.

## 11. Защита незасохранённого ввода

**Живое обновление никогда не заменяет форму с несохранённым вводом.** Форма
решения КО, форма анализа ТО с динамическими строками, поле нового
комментария, диалоги возврата и форма вложения находятся вне заменяемых
блоков. Заменяются только read-only блоки: сводка, история, список
комментариев, связанные мероприятия.

«Грязное» состояние выставляется только настоящим жестом пользователя
(`input`/`change` или добавление/удаление динамической строки). Программная
замена фрагмента не порождает событий и не может дать ложное срабатывание.

Если акт изменился извне, пока форма «грязная», показывается постоянный баннер
конфликта, а введённый текст остаётся нетронутым и доступным для копирования.
При `act.status_changed` дополнительно отключаются кнопки отправки workflow —
обычные поля остаются редактируемыми, а настоящей защитой остаются блокировка
строки и перепроверка статуса на сервере.

«Чистая» рабочая вкладка после `act.status_changed` заменяется актуальной
серверной разметкой; общий реестр инициализаторов заново подключает
динамические формы, не регистрируя обработчики повторно.

Ошибка фрагмента не очищает интерфейс: текущая разметка и счётчики остаются,
следующая сверка приводит их в порядок.

Toast показывает только `notification.created`. `task.*`, `act.*` и
`comment.created` обновляют блоки молча — пользователь и так получает
уведомление там, где этого требуют бизнес-правила.

## 12. Отказ Redis

| Что произошло | Поведение |
| --- | --- |
| Redis недоступен в момент публикации | бизнес-операция уже зафиксирована; ошибка логируется и подавляется |
| Redis недоступен при открытии потока | `503` на preflight, без зависания |
| Redis упал во время потока | контролируемое завершение потока, клиент переподключается через объявленный `retry` |
| Redis перезапущен | сообщения этого интервала потеряны; состояние досчитывается сверкой |
| Никто не подписан на канал | нормальное состояние транспорта, не ошибка |

Redis — транспорт, а не хранилище: события не сохраняются, не переигрываются и
не подтверждаются. Persistence для real-time не требуется. Потеря сообщения
означает отложенное обновление интерфейса, а не потерю данных.

## 13. Диагностика

```powershell
python manage.py check                     # системные проверки конфигурации real-time
python manage.py check_realtime_transport  # PING и round trip через одноразовый канал
python manage.py check_sse_db_connections  # соединения с базой при открытых потоках
python manage.py profile_realtime_sync     # стоимость /realtime/sync/ по ролям
```

`check` ловит опасную конфигурацию (`realtime/checks.py`): включённый real-time
на Noop publisher, отсутствующий или некорректный Redis URL, отсутствующий
`ASGI_APPLICATION`, heartbeat не короче времени жизни соединения, некорректные
интервалы polling и аренды лидера, недопустимый префикс каналов. При
`DEBUG=False` опасные комбинации — ошибки, а не предупреждения.

`check_realtime_transport` публикует случайный токен в одноразовый
диагностический канал, читает его обратно и измеряет round trip. Readiness-проба
`/health/ready/` выполняет только PING и это не заменяет: Redis может отвечать,
а доставка при этом не работать — например, если рядом развёрнуто приложение с
другим `REALTIME_CHANNEL_PREFIX`.

Логи и события `realtime`, а также правила по объёму записей — в
[operations.md](operations.md). Требования к среде (ASGI, reverse proxy,
закрытая служба Redis) — в [deployment.md](deployment.md).

## 14. Границы best-effort доставки

Что подсистема **не** обещает:

- гарантированную доставку, подтверждения и порядок сообщений;
- хранение и переигрывание пропущенных событий, transactional outbox;
- корректность интерфейса без `/realtime/sync/` — именно сверка делает
  состояние верным;
- работу под WSGI: `runserver` и WSGI-сервер поток не удержат;
- присутствие, чат и индикатор набора текста.

WebSocket, Django Channels, React и любой сборщик здесь не используются;
добавляются они только отдельным архитектурным решением.
