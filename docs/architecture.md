# Архитектура

Система — монолитное Django-приложение с серверным рендерингом. Никакого
фронтенд-фреймворка, сборщика и внешней шины сообщений в ней нет.

## 1. Технологический контур

| Слой | Реализация |
| --- | --- |
| Интерфейс | Django Templates + vanilla JavaScript (без npm, без сборки) |
| Приложение | Django, синхронные вьюхи; SSE-поток — асинхронная вьюха |
| Сервер | ASGI (Uvicorn); `ASGI_APPLICATION = 'ecosystem.asgi.application'` |
| База данных | PostgreSQL в production, SQLite в разработке |
| Real-time транспорт | Redis Pub/Sub → Server-Sent Events |
| Почта | корпоративный SMTP relay, отправка отдельной management-командой |
| Файлы | публичная статика и protected media |

Точные версии — в `requirements.txt`. Полный список переменных окружения — в
`.env.example` и `ecosystem/settings.py`.

## 2. Схема

```
        браузер
   Django Templates + vanilla JS
      │  HTTP            │  EventSource
      │  (страницы,      │  GET /realtime/events/
      │   фрагменты,     │
      │   /realtime/sync/)
      ▼                  ▼
 ┌───────────────────────────────────┐
 │      ASGI (Uvicorn) + Django      │
 │  views → services → models        │
 │  permissions на каждом входе      │
 └───────┬───────────┬───────────┬───┘
         │           │           │
   PostgreSQL      Redis     MEDIA_ROOT
  источник      Pub/Sub      protected
   истины      best-effort   вложения
                    ▲
                    │ publish_after_commit
                    │
         NotificationDelivery ──► management-команда
                                  process_notification_deliveries ──► SMTP
```

Redis обслуживает **только** real-time. Доставка писем через него не идёт:
письма ставятся в очередь `NotificationDelivery` в базе и отправляются
отдельной командой. Celery не используется.

## 3. Приложения и ответственность

| Приложение | Ответственность |
| --- | --- |
| `ecosystem` | настройки, URLconf, ASGI/WSGI, deployment-проверки, health, логирование, middleware. Моделей нет |
| `accounts` | `Department`, `UserProfile` (роль, подразделение), вход в систему |
| `references` | справочники: операции, виды дефектов, статусы актов и задач, приоритеты; `seed_references` |
| `acts` | акты, дефекты, корневые проработки, корректирующие мероприятия, история, комментарии, вложения, workflow, права |
| `tasks` | задачи, созданные при утверждении акта, их исполнители и завершение |
| `notifications` | внутренние уведомления, дедупликация, маршрутизация получателей, очередь email-доставок |
| `realtime` | контракт событий, targets, каналы, публикация, SSE-endpoint, сверка ревизий. Моделей и миграций нет |
| `maintenance` | технические команды: проверки готовности, логирования, документации, инструменты переноса. Моделей и миграций нет |

## 4. Допустимые направления зависимостей

```
references  ←  acts  ←  tasks
accounts    ←  acts
acts, tasks, notifications  →  realtime.emitters
notifications  ←  acts (через отложенный импорт внутри сервиса)
realtime  →  acts.permissions, tasks.permissions, notifications.services
```

Правила:

- `references` и `accounts` ни от кого из бизнес-приложений не зависят;
- `tasks` зависит от `acts`, обратной зависимости на уровне модулей нет:
  `acts.services` импортирует `tasks.models` локально, внутри функции;
- `realtime` не содержит собственных бизнес-правил. Видимость он берёт из
  `acts.permissions` / `tasks.permissions`, а состав получателей — из
  `notifications.services`. Второго набора правил маршрутизации в проекте нет;
- бизнес-код не импортирует клиент Redis. Транспорт скрыт за
  `realtime.publisher` и выбирается настройкой `REALTIME_PUBLISHER_BACKEND`.

## 5. Слои внутри приложения

**Модели** (`models.py`) — структура данных и инварианты уровня базы:
уникальность номера акта, уникальность пары «мероприятие — исполнитель»,
согласованность состояния прочтения уведомления.

**Права** (`permissions.py`) — единственное место, где решается «кто что
видит и что может сделать». Возвращают либо булев ответ по объекту
(`can_view_act`, `can_complete_task`), либо queryset/`Q` для списков. Шаблоны
и вьюхи никогда не воспроизводят эти правила самостоятельно.

**Селекторы** (`selectors.py`) — сборка состояния страницы для чтения.
Полная страница и её фрагмент собираются одним и тем же строителем состояния,
поэтому обновлённый блок не может разойтись с перезагрузкой страницы.

**Сервисы** (`services.py`) — единственное место изменения workflow. Каждый
критичный переход открывает `transaction.atomic()`, заново загружает и
блокирует акт (`select_for_update`), только после этого перепроверяет права и
статус и работает с полученным заблокированным экземпляром.

**Вьюхи** (`views.py`) — разбор запроса, вызов прав и сервисов, рендеринг.
Бизнес-логики не содержат.

## 6. События после commit

Событие real-time публикуется явным вызовом эмиттера из сервиса — никогда из
сигнала `post_save`. Сигнал сработал бы при загрузке фикстур, при техническом
`save()` и до того, как связанные объекты существуют.

`publish_after_commit()` регистрирует публикацию через `transaction.on_commit`,
поэтому откат транзакции не публикует ничего. Отказ транспорта происходит уже
после фиксации бизнес-операции и по умолчанию логируется и подавляется:
сохранённые данные не страдают.

Событие сообщает **что изменилось**, а не **каким стало**: только
идентификаторы и безопасные технические метаданные. Подробности — в
[realtime.md](realtime.md).

## 7. Статика и protected media

`STATIC_ROOT` — публичный каталог: CSS, JavaScript, изображения интерфейса,
собираемые `collectstatic` и раздаваемые веб-сервером.

`MEDIA_ROOT` — **protected media**: вложения актов. Они выдаются только через
`acts.views.act_download_attachment`, который проверяет права на каждый
запрос. Прямая раздача `MEDIA_ROOT` веб-сервером обошла бы видимость акта
целиком. Каталоги обязаны быть разными.

## 8. Источники истины

| Что | Источник |
| --- | --- |
| Данные приложения | PostgreSQL |
| Права и видимость | `acts/permissions.py`, `tasks/permissions.py` |
| Бизнес-аудит действий | `ActHistoryEvent` (вкладка «История акта») |
| Диагностика | журнал приложения — может быть ротирован и удалён |
| Содержимое интерфейса | обычные Django-endpoint'ы с проверкой прав |
| Real-time событие | сигнал «перезапроси», а не источник HTML и не источник прав |
| Redis Pub/Sub | транспорт best-effort: события не хранятся, не переигрываются и не подтверждаются |

Клиент, получивший событие, всегда перезапрашивает данные обычным
авторизованным запросом. Пропущенное сообщение означает отложенное обновление
интерфейса, а не потерю данных: состояние досчитывается через
`/realtime/sync/`.
