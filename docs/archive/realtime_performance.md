# Производительность real-time: методика и измерения

> **Внимание: исторический документ.**
>
> - он описывает состояние проекта на момент написания и может не
>   соответствовать текущему коду;
> - он не является инструкцией для новых изменений;
> - актуальные документы перечислены в [docs/index.md](../index.md).

Документ описывает, **как измерять** стоимость real-time подсистемы и **что
уже измерено**. Он намеренно разделяет две вещи: воспроизводимый метод и
конкретные числа, полученные в конкретной среде. Число, снятое на SQLite, не
является утверждением о производительности PostgreSQL.

## 1. Принципы

1. **Сначала измерение, потом оптимизация.** Индекс добавляется только после
   `EXPLAIN (ANALYZE, BUFFERS)` на реалистичном наборе данных, а не потому,
   что колонка «выглядит подходящей».
2. **Число запросов важнее микросекунд.** Запрос, число которого растёт вместе
   с данными, — это дефект; запрос, который просто медленный, — это вопрос
   индекса или объёма.
3. **Отчёты не содержат бизнес-данных.** Ни имён, ни email, ни номеров актов,
   ни текстов задач и комментариев, ни строк подключения, ни паролей.
4. **SQLite ≠ PostgreSQL.** Планы выполнения и `EXPLAIN ANALYZE` имеют смысл
   только на настоящей PostgreSQL. Инструменты в этом репозитории отказываются
   делать вид, что это не так.

## 2. Тестовый набор данных

`realtime/management/commands/seed_performance_dataset.py` — только для среды
разработки и тестирования.

```powershell
# Отдельная одноразовая база, рабочая db.sqlite3 не затрагивается
$env:SQLITE_DB_PATH = "transfer\perf.sqlite3"
python manage.py migrate
python manage.py seed_references

# По умолчанию dry-run: показывает план и ничего не пишет
python manage.py seed_performance_dataset --users 50 --acts 5000 --tasks 10000 `
    --comments 20000 --history 20000 --notifications-per-user 20

# Запись требует явного --execute
python manage.py seed_performance_dataset --users 50 --acts 5000 --tasks 10000 `
    --comments 20000 --history 20000 --notifications-per-user 20 --execute
```

Рекомендуемый профиль: 50 пользователей, ~5 000 актов, ~10 000 задач,
~20 000 комментариев, ~20 000 history events, ~20 уведомлений на пользователя.

Правила безопасности команды:

- dry-run по умолчанию, запись только с `--execute`;
- при `DEBUG=False` отказывается работать без
  `--i-know-this-is-not-development`;
- всё создаётся в одной транзакции;
- каждая созданная строка помечена `PERF-SYNTHETIC` в тексте, а номера актов
  имеют вид `PERF-SYNTHETIC-YYYY-NNNNNN` — синтетику невозможно спутать с
  рабочими данными;
- сгенерированные учётные записи получают **неиспользуемый пароль**
  (`set_unusable_password()`): они существуют, чтобы владеть строками, а не
  чтобы входить в систему;
- production-данные не используются и не копируются никогда.

## 3. Профилирование

```powershell
python manage.py profile_realtime_sync --user <id> --repeat 10
python manage.py profile_realtime_sync --user <id> --repeat 10 --json-report perf.json
python manage.py profile_realtime_sync --user <id> --explain           # только PostgreSQL
python manage.py profile_realtime_sync --user <id> --explain-analyze   # отдельный явный флаг
```

Команда только читает. Она измеряет восемь сценариев: `/realtime/sync/`
целиком, каждый из пяти revision-запросов по отдельности, список задач и
реестр актов. Для каждого выводится число SQL-запросов и min/avg/p95/max
задержки; `(!)` рядом со строкой означает, что число запросов менялось между
повторами — обычно признак ленивой загрузки, зависящей от данных.

JSON-отчёт содержит только: версию схемы, vendor базы, **роль** пользователя,
флаг полного доступа, число повторов и измерения. Ни имени пользователя, ни
идентификаторов, ни текстов.

Локальные отчёты и планы — рабочие артефакты, а не часть репозитория: держите
их вне Git (`transfer\`, временные каталоги). В документацию попадают только
безопасные сводные показатели и принятые решения.

## 4. Бюджет запросов `/realtime/sync/`

Зафиксирован тестом `realtime/tests/test_sync.py` (`FIXED_SYNC_QUERIES`) и
проверяется для ролей OTK, KO, TO и manager.

| # | Запрос |
| --- | --- |
| 1 | notifications: total + unread (filtered Count) + max(created_at) + max(read_at) |
| 2 | tasks: totals, timestamps, assignments, `Max(assignees.pk)` |
| 3 | tasks: распределение по статусам |
| 4 | acts: active/archived totals и timestamps как filtered aggregates |
| 5 | acts: распределение активных по статусам |
| 6 | comments: count + max(created_at) по подзапросу видимых актов |
| 7 | history: count + max(created_at) по подзапросу видимых актов |
| 8 | activities: связанные задачи — totals, timestamps, assignments |
| 9 | activities: распределение связанных задач по статусам |

**Итого 9 запросов**, при целевом бюджете «не более 10». Session
authentication и однократное разрешение `user.userprofile` сюда не входят —
это работа запроса, а не сервиса.

Ключевое свойство: число запросов **не зависит** от объёма данных. Ни один
запрос не материализует идентификаторы в Python — видимые акты передаются в
comments/history как **подзапрос** (`act__in=<queryset>`), а не как список PK.
Это закреплено тестом
`test_a_much_larger_dataset_costs_exactly_the_same_number_of_queries`.

### Что изменилось

| | до STAB-2 | после |
| --- | --- | --- |
| запросов в `build_sync_state()` | 13 | **9** |
| материализация PK актов в Python | да, два `list(values_list(...))` | нет |
| unread-уведомления | отдельный `.count()` | filtered aggregate в том же запросе |
| active/archive акты | два отдельных aggregate | один filtered aggregate |
| замена исполнителя двигает revision | нет | да (`Max(assignees.pk)`) |

### Fingerprint назначений

`Count(assignees)` не отличает «заменили исполнителя A на B» от «ничего не
произошло». Добавлен `Max(assignees__pk)`: новая строка `TaskAssignee` всегда
получает больший id, поэтому замена двигает токен при неизменном количестве.
Стоимость — ещё один агрегат по join, который база и так выполняет; списка
идентификаторов исполнителей в Python по-прежнему нет.

Изменение состава исполнителей выполняется только через
`tasks.services.replace_task_assignees()`, которое транзакционно и **явно**
обновляет `Task.updated_at` (без signals).

## 5. Чтение EXPLAIN

`--explain` доступен только на PostgreSQL; на любом другом backend команда
печатает понятное сообщение и не выдаёт результат за план PostgreSQL.
`--explain-analyze` требует отдельного флага, потому что действительно
выполняет запрос.

На что смотреть:

- `Seq Scan` по большой таблице внутри агрегата — кандидат на индекс;
- `Rows Removed by Filter` намного больше возвращённых строк — фильтр
  неселективен по текущим индексам;
- `Buffers: shared read=` заметно больше `hit=` — данные не в кэше, реальный
  дисковый ввод-вывод;
- разница между `estimated` и `actual rows` на порядок — устаревшая
  статистика, `ANALYZE` до любых выводов об индексах.

## 6. Критерии добавления индекса

Индекс добавляется, только если выполнены **все** условия:

1. есть реальный `EXPLAIN (ANALYZE, BUFFERS)` на наборе из раздела 2;
2. виден дорогой scan именно в горячем запросе;
3. индекс заметно меняет план или время (не единицы процентов);
4. стоимость записи и объём оправданы выигрышем на чтении.

Кандидаты, которые имеет смысл проверить (список для проверки, **не** список
к добавлению): `Act(status, updated_at)`, `Act(created_by, status, updated_at)`,
`Task(status, updated_at)`, `Task(due_date, status)`,
`ActComment(act, created_at)`, `ActHistoryEvent(act, created_at)`.

Если измерение не показало улучшения — индекс не добавляется, и пустая
миграция не создаётся.

## 7. Redis

- `REALTIME_REDIS_CONNECT_TIMEOUT_SECONDS` и
  `REALTIME_REDIS_SOCKET_TIMEOUT_SECONDS` по умолчанию **1 с** (было 5).
  Публикация идёт из `on_commit`, то есть внутри пользовательского запроса:
  недоступный Redis должен стоить запросу ~1 секунду, а не 5. Событие
  best-effort, клиент всё равно досчитает состояние сверкой.
- Публикация выполняется одним `pipeline(transaction=False)`: событие
  сериализуется один раз, все каналы уходят одним сетевым round trip.
  `MULTI/EXEC` не используется — это добавило бы две команды и гарантии,
  которые best-effort транспорту не нужны.
- Публикуются только каналы, на которые кто-то может подписаться, — сегодня
  это исключительно `user:<id>`. `act:<id>` остаётся маршрутной подсказкой в
  контракте события, но в Redis не пишется: браузеру запрещено подписываться
  на комнату акта, пока она не авторизована через `can_view_act`.
- `REALTIME_REDIS_SLOW_PUBLISH_MS` (по умолчанию 250) — порог, после которого
  публикация логируется как `realtime.slow_publish` с типом события, числом
  каналов и длительностью. Ни payload, ни Redis URL, ни учётные данные в лог
  не попадают.

## 8. SSE и соединения PostgreSQL

Вопрос: удерживает ли долгоживущий SSE-поток соединение с PostgreSQL — и тем
более `idle in transaction`? Поток живёт до
`REALTIME_MAX_CONNECTION_SECONDS`, поэтому 50 потоков, удерживающих по
соединению, исчерпали бы `max_connections` задолго до целевого числа
пользователей.

```powershell
python manage.py check_sse_db_connections --label before --json-report before.json
# в другом терминале запустить нагрузочную проверку из раздела 9, затем:
python manage.py check_sse_db_connections --label during --json-report during.json
# остановить прогон, подождать несколько секунд:
python manage.py check_sse_db_connections --label after  --json-report after.json
```

Команда только читает `pg_stat_activity`, отдельно считает `active`, `idle`,
`idle in transaction` и `idle in transaction (aborted)`, и на не-PostgreSQL
backend отказывается работать вместо того, чтобы выдать бессмысленный
результат.

Ожидаемая гарантия: 20–50 открытых потоков **не** создают 20–50 соединений в
состоянии `idle in transaction`, а после закрытия потоков число соединений
возвращается к исходному. После аутентификации поток работает только с Redis
и к базе не обращается.

**Принудительное закрытие Django DB connection перед началом стрима намеренно
не добавлено**: сначала измерение, потом решение. Если замер покажет, что
поток действительно удерживает соединение, минимальное безопасное освобождение
добавляется отдельно — перед началом стрима, никогда не посреди ORM-операции —
вместе с тестом и обоснованием.

## 9. Нагрузочная проверка

```powershell
$env:REALTIME_SMOKE_PASSWORD = "<пароль тестовой учётной записи>"
python scripts\realtime_load_smoke.py --base-url http://127.0.0.1:8000 `
    --username smoke_user --connections 50 --seconds 1800 `
    --json-report transfer\smoke.json
```

Чек-лист прогона: число соединений и длительность; сколько подключений
успешно; сколько переподключений; ошибки по типам; при наличии событий —
медиана и максимум задержки; снимки `pg_stat_activity` до, во время и после.
Во время прогона стоит перезапустить Redis и ASGI-сервер и закрыть
вкладку-лидера — соединения должны восстановиться, а счётчики сойтись с базой
после очередной сверки.

Скрипт отказывается работать против нелокального адреса без явного
подтверждения, не хранит пароль и не читает браузерные cookie; JSON-отчёт
содержит только host, счётчики и тайминги.

## 10. Фактически выполненные измерения

**Среда:** локальная разработка, Windows, **SQLite** (отдельная одноразовая
база через `SQLITE_DB_PATH`, рабочая `db.sqlite3` не затрагивалась).
**Набор данных:** ровно профиль из раздела 2 — 50 пользователей, 5 000 актов,
10 000 задач, 20 000 комментариев, 20 000 history events, 1 000 уведомлений.
`--repeat 10`.

Число SQL-запросов (одинаково для всех проверенных ролей, стабильно между
повторами):

| Сценарий | Запросов |
| --- | --- |
| `/realtime/sync/` целиком | **9** |
| revision notifications | 1 |
| revision tasks | 2 |
| revision acts | 2 |
| revision comments | 2 |
| revision activities | 2 |
| список задач | 4 |
| реестр актов | 7 |

Задержка `/realtime/sync/`, avg / p95 (миллисекунды, **SQLite**):

| Роль | avg | p95 |
| --- | --- | --- |
| OTK | 17 | 18 |
| KO | 26 | 27 |
| TO | 27 | 29 |
| manager (полный доступ) | 79 | 81 |

Наблюдение: у роли с полным доступом дороже всего revision comments (~44 мс) —
это агрегаты по 20 000 комментариев и 20 000 history events, — и отдельно
стоит отметить реестр актов (~350 мс), который к `/realtime/sync/` отношения
не имеет: это обычная страница, рендерящая 5 000 строк.

### Что измерено **не** было

- **PostgreSQL**: сервер в этой среде недоступен. `EXPLAIN` и
  `EXPLAIN (ANALYZE, BUFFERS)` **не выполнялись**. Любое утверждение о планах,
  индексах и производительности PostgreSQL требует повторить разделы 3 и 5 на
  настоящей PostgreSQL.
- **Индексы**: по этой же причине **не добавлены** и миграция не создана.
  Числа выше получены на SQLite и не являются обоснованием индекса для
  PostgreSQL.
- **Redis**: сервер недоступен, поэтому реальная latency публикации и выигрыш
  от pipeline **не измерены** end-to-end. Поведение publisher'а (одна
  сериализация, один pipeline, `transaction=False`, только `user:` каналы,
  slow-publish предупреждение) покрыто unit-тестами на фейковом клиенте.
- **SSE и `pg_stat_activity`**: требует одновременно PostgreSQL, Redis и
  ASGI-сервер — **не выполнено**. Команда и процедура подготовлены, гарантия
  из раздела 8 остаётся непроверенной.
- **Нагрузочный прогон** `realtime_load_smoke.py`: по той же причине **не
  выполнялся**.

Эти проверки — обязательный ручной шаг перед любым утверждением о готовности
к пилоту.
