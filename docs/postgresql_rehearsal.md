# Репетиция переноса SQLite → PostgreSQL

Документ описывает **полную репетицию** переноса на копиях данных и пустой
тестовой базе PostgreSQL. Репетиция ничего не переключает: рабочее приложение
продолжает работать на SQLite, а production-переезд остаётся отдельным этапом
с согласованным окном простоя.

Сама механика переноса (пакет, импорт, сверка) описана в
[Перенос данных из SQLite в PostgreSQL](postgresql_migration.md); здесь —
порядок репетиции, чтение отчёта и критерии допуска.

## 1. Подготовка source-копий

Экспорт выполняется из **остановленной копии** базы и из **копии media**, а не
из рабочих файлов: иначе можно получить частично записанные данные и файлы,
изменившиеся во время экспорта.

1. Остановите приложение: `runserver` / WSGI-процесс, планировщик очереди email
   (systemd timer или Windows Task Scheduler), любые фоновые запуски
   `manage.py`.
2. Скопируйте базу и медиа:

```powershell
New-Item -ItemType Directory -Force transfer | Out-Null
Copy-Item db.sqlite3 transfer\db-copy.sqlite3
Copy-Item -Recurse media transfer\media-copy
```

3. Убедитесь, что копии больше никем не изменяются. Приложение можно запустить
   обратно: дальше работа идёт только с копиями.

Каталог `transfer/` уже в `.gitignore` — копии и пакет содержат реальные
рабочие данные и в репозиторий не попадают.

## 2. Подготовка тестовой PostgreSQL

Сервер, база и пользователь создаются отдельно (см.
[Подготовка к PostgreSQL](postgresql_preparation.md)). Для репетиции нужна
**отдельная пустая** база — не production и не CI.

```powershell
$env:DATABASE_ENGINE = "postgresql"
$env:DB_NAME = "quality_rehearsal"
$env:DB_USER = "quality_rehearsal"
$env:DB_PASSWORD = "<пароль из окружения>"
$env:EMAIL_NOTIFICATIONS_ENABLED = "false"
$env:MEDIA_ROOT_PATH = "transfer\target-media"

python manage.py migrate
```

Миграции данных создают строки в `references.ActStatus` (`ARCHIVED`,
`OTK_REVIEW`) и `references.TaskStatus` (`IN_PROGRESS`, `COMPLETED`). Пакет
содержит собственные копии этих строк, поэтому перед импортом их нужно убрать:

```powershell
python manage.py prepare_empty_migration_target
python manage.py prepare_empty_migration_target --execute --confirm "ОЧИСТИТЬ ТЕСТОВУЮ БАЗУ"
```

Первый запуск — dry-run: он печатает точный список таблиц и строк и ничего не
меняет. Команда удаляет **только** перечисленные выше коды справочников,
отказывается работать при любых пользовательских данных, не использует `flush`
и не трогает пользователей, акты, задачи, уведомления и файлы.

## 3. Переменные окружения

Все секреты передаются **только** через окружение. Пароль никогда не
передаётся аргументом командной строки и не попадает в отчёты.

| Переменная | Назначение |
| --- | --- |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | обязательные реквизиты тестовой PostgreSQL |
| `DB_HOST`, `DB_PORT` | по умолчанию `127.0.0.1` и `5432` |
| `EMAIL_NOTIFICATIONS_ENABLED` | должна оставаться `false` на всё время репетиции |

`DATABASE_ENGINE`, `SQLITE_DB_PATH` и `MEDIA_ROOT_PATH` оркестратор
подставляет сам для каждого этапа — задавать их вручную не нужно.

## 4. Команда запуска

```powershell
$env:DB_NAME = "quality_rehearsal"
$env:DB_USER = "quality_rehearsal"
$env:DB_PASSWORD = "<пароль из окружения>"

python scripts\run_postgresql_rehearsal.py `
  --source-db transfer\db-copy.sqlite3 `
  --source-media transfer\media-copy `
  --bundle transfer\bundle `
  --target-media transfer\target-media `
  --json-report transfer\rehearsal-report.json `
  --markdown-report transfer\rehearsal-report.md
```

Дополнительные параметры:

- `--allow-default-source-db` — разрешить репетицию на рабочем `db.sqlite3`.
  Без него указание рабочего файла отклоняется до запуска любого этапа.
- `--diagnostic-missing-media` — диагностический режим: собрать и осознанно
  принять неполный пакет с отсутствующими файлами вложений. Такой перенос
  никогда не считается полным и блокирует production-переезд.

Каждый этап запускается **отдельным процессом** `manage.py`. Это не
оптимизация, а требование: SQLite и PostgreSQL выбираются переменными
окружения, которые Django читает один раз при старте, поэтому один процесс не
может корректно быть и тем и другим.

## 5. Этапы оркестратора

Этапы выполняются строго последовательно; первый неуспешный останавливает всё
остальное.

| № | Этап | Backend | Что делает |
| --- | --- | --- | --- |
| 1 | `source_preflight` | SQLite | `check_migration_source` на копии базы |
| 2 | `export_bundle` | SQLite | `export_migration_bundle` из копии базы и копии media |
| 3 | `validate_bundle` | SQLite | `verify_migration_bundle --validate-only` — повторная проверка пакета |
| 4 | `target_preflight` | PostgreSQL | `check_migration_target` на пустой тестовой базе |
| 5 | `import_dry_run` | PostgreSQL | `import_migration_bundle --dry-run` |
| 6 | `import_bundle` | PostgreSQL | реальный импорт |
| 7 | `verify_bundle` | PostgreSQL | `verify_migration_bundle` — итоговая сверка |
| 8 | `smoke_checks` | PostgreSQL | `run_postgresql_smoke_checks` |
| 9 | отчёт | — | JSON и Markdown |

### Что проверяет source preflight

Файл базы существует и читается; используется отдельная копия, а не рабочий
`db.sqlite3`; backend действительно SQLite; нет неприменённых миграций;
`PRAGMA integrity_check` возвращает `ok`; соблюдены ключевые реляционные
инварианты; стандартные номера актов уникальны; `ActNumberSequence` не
отстаёт; все пути `ActAttachment` безопасны; каждый файл вложения есть в
выбранном source media; фактический размер файла совпадает с заполненным
`ActAttachment.file_size`; количество моделей, записей и вложений
зафиксировано. Ничего не изменяется.

### Что проверяет target preflight

Backend — PostgreSQL; все миграции применены; `EMAIL_NOTIFICATIONS_ENABLED`
выключена; все переносимые таблицы пусты; `MEDIA_ROOT` пуст или отсутствует;
база доступна для чтения и записи (пробная транзакция всегда откатывается);
у пользователя базы есть `CONNECT`, `TEMPORARY` и `SELECT/INSERT/UPDATE/DELETE`
на переносимых таблицах; версия PostgreSQL доступна для отчёта; по данным
предыдущего rehearsal-отчёта нет незавершённого импорта.

### Что проверяют smoke-проверки

Read-only: пользователи и профили, активные и архивные акты, дефекты, история
и комментарии, анализ ТО с мероприятиями и исполнителями, задачи и их
исполнители, уведомления и email-доставки, permission-функции на реальных
данных, существование всех файлов `ActAttachment`, типовые ORM-запросы
реестров и детальных страниц.

Запись — внутри транзакции с обязательным откатом: создание временного
пользователя и автоматическое появление `UserProfile`, создание акта и выдача
следующего автоматического номера, дефект, комментарий, событие истории,
корневая проработка с мероприятием, задача с исполнителем, внутреннее
уведомление, завершение тестовой задачи, проверка ограничений и связей. После
отката проверяется, что ни одна тестовая запись не сохранилась. Email не
отправляется: `EMAIL_NOTIFICATIONS_ENABLED` остаётся `false`, а доставки не
создаются.

## 6. Чтение отчёта

Оркестратор всегда пишет два файла — и при успехе, и при ошибке.

`rehearsal-report.json` — для машинной обработки. `rehearsal-report.md` — для
ручного просмотра. Оба содержат:

- время запуска и завершения, ОС, Git commit (если доступен локально);
- версии Python, Django, Psycopg, SQLite и PostgreSQL;
- размер копии SQLite, число и объём файлов source media;
- количество моделей, строк и вложений;
- длительность каждого этапа;
- итоговые хеши и количества по каждой модели;
- результат сброса последовательностей PostgreSQL;
- состояние `ActNumberSequence` (создано / поднято / без изменений);
- результат реляционной сверки;
- результат read- и write-smoke-проверок;
- отсутствующие файлы вложений;
- предупреждения;
- общий статус;
- оценку минимального окна простоя;
- блокирующие production-переезд проблемы.

Отчёты **не** содержат паролей, `SECRET_KEY`, содержимого записей, хешей
паролей, содержимого вложений и абсолютных серверных путей: известные
секретные значения вырезаются из любого захваченного вывода, а пути
сокращаются до последних двух компонентов.

При ошибке в отчёте фиксируются этап, команда, длительность и безопасный текст
ошибки, а также рекомендуемое действие для повторной попытки. Копии SQLite,
копия media и миграционный пакет не удаляются — они нужны для разбора.

## 7. Ручной checklist

Отчёт не заменяет ручную проверку. Выполните её на тестовой PostgreSQL и
зафиксируйте результат каждого пункта (дата, исполнитель, `ОК` / `не ОК` +
комментарий).

| № | Проверка | Результат |
| --- | --- | --- |
| 1 | Вход под существующим пользователем (реальная учётная запись, не демо) | |
| 2 | Реестр активных актов: `Мои акты` и `Все акты`, фильтры, сортировка | |
| 3 | Архив актов: содержимое и дата архивирования | |
| 4 | Несколько дефектов в разных актах: поля, цех/поставщик, количества | |
| 5 | Решение КО: сохранённое значение и его отображение | |
| 6 | Анализ ТО: корневые причины, мероприятия, подразделения, исполнители | |
| 7 | История акта и комментарии: порядок, авторы, даты | |
| 8 | Скачивание вложений через защищённые ссылки | |
| 9 | Задачи: `Мои задачи`, `Все задачи`, `Архив`, сроки и просрочка | |
| 10 | Уведомления: счётчик, меню колокольчика, состояние прочтения | |
| 11 | Создание тестового акта | |
| 12 | Проверка следующего номера: он идёт за максимальным реальным номером | |
| 13 | Полный маршрут тестового акта: ОТК → КО → ТО → проверка ОТК → утверждение → задача → завершение | |

Тестовый акт и задачу, созданные в пунктах 11–13, после проверки следует
удалить или оставить только в тестовой базе — в production они не переносятся.

## 8. Оценка окна простоя

Отчёт печатает две величины:

- `measured_seconds` — суммарная длительность этапов, требующих остановки
  приложения (source preflight, экспорт, проверка пакета, dry-run, импорт,
  сверка);
- `estimated_window_seconds` — оценка минимального окна: замеренное время
  плюс 50% запаса плюс 10 минут на ручные действия.

Оценка — нижняя граница. К ней нужно добавить время на остановку приложения,
копирование базы и media, ручной checklist и, при необходимости, откат.
Реальное окно планируется по худшей из нескольких репетиций, а не по лучшей.

## 9. План отката

- Исходные `db.sqlite3` и `media` остаются **неизменными** на всех этапах:
  репетиция работает только с копиями и с тестовой PostgreSQL.
- До успешной итоговой сверки и пройденного ручного checklist рабочее
  приложение не переключается на PostgreSQL.
- При любой ошибке тестовая PostgreSQL и её `MEDIA_ROOT` пересоздаются с нуля,
  после чего репетиция повторяется из того же (или пересобранного) пакета.
  Повторный импорт в уже заполненную базу невозможен — таблицы не пусты.
- При частичной активации media база зафиксирована, а файлы — нет. Нужно либо
  вручную скопировать файлы из `bundle/media` в `MEDIA_ROOT` и повторить
  сверку, либо пересоздать базу и повторить перенос целиком.
- **После начала реальной работы пользователей в PostgreSQL возврат к старой
  SQLite без обратного переноса запрещён**: данные, введённые в PostgreSQL, в
  SQLite отсутствуют. Обратная миграция PostgreSQL → SQLite не реализована.
- Production-переключение — отдельный этап: адрес приложения, WSGI/ASGI,
  reverse proxy, HTTPS и резервное копирование этой репетицией не
  затрагиваются.

## 10. Критерии допуска к production-переносу

Переезд можно планировать только когда одновременно выполнено всё:

1. Общий статус отчёта — `УСПЕШНО`, список блокирующих проблем пуст.
2. Пакет полный: `missing_media` пуст, диагностический режим не
   использовался.
3. Итоговая сверка прошла: совпали количества, максимальные PK и хеши по
   каждой модели, все файлы media проверены по размеру и SHA-256, реляционных
   проблем нет.
4. `ActNumberSequence` синхронизирована, отстающих счётчиков нет.
5. Read- и write-smoke-проверки пройдены, тестовые данные не сохранились.
6. Ручной checklist выполнен полностью и зафиксирован.
7. Оценка окна простоя согласована с владельцем процесса.
8. План отката подтверждён, резервные копии `db.sqlite3` и `media` сделаны и
   проверены на восстановление.

Успешная репетиция подтверждает работоспособность инструментов и пригодность
данных — она **не означает**, что production-переезд выполнен.

## 11. Очистка

Пакет, копии и отчёты содержат реальные рабочие данные:

```powershell
Remove-Item -Recurse -Force transfer
```

Хранить их дольше, чем нужно для разбора, не следует. В Git они не попадают.
