# Операционное логирование

Документ описывает журнал приложения для пилотной эксплуатации: категории,
формат строки, `request_id`, настройки, ротацию, срок хранения, порядок
расследования инцидента и передачу логов ИТ-службе.

**Основной способ хранения — ротируемый текстовый файл UTF-8.** Он лежит на
сервере, читается человеком без внешних инструментов и не требует ни одной
дополнительной службы. Консольный вывод сохраняется рядом: его собирает
process manager, и через него позже можно подключить централизованный сбор,
не меняя ни строки бизнес-кода.

Используется только стандартный `logging` из Python. ELK, Loki, Sentry,
Graylog и любой другой внешний сервис этим этапом **не** добавляются.

## 1. Категории логов

| Logger | Что записывает |
| --- | --- |
| `ecosystem.request` | одна строка на изменяющий, медленный или неуспешный HTTP-запрос |
| `ecosystem.startup` | `application.started` при запуске процесса, `logging.probe` |
| `ecosystem.workflow` | переходы актов и операции с задачами |
| `ecosystem.attachments` | загрузка, скачивание, отказ в доступе, ошибка хранения |
| `notifications.email` | запуск и итог worker'а, отправка, retry, отказ |
| `realtime` | жизненный цикл SSE, публикация в Redis, медленный sync |
| `deployment` | health-пробы и readiness |
| `maintenance` | инструменты переноса данных |
| `django.request`, `django.security` | необработанные исключения, 4xx/5xx, CSRF, Host |

Уровень задаётся `LOG_LEVEL`, для `realtime` — отдельно `REALTIME_LOG_LEVEL`.

## 2. Формат строки

```
[timestamp] LEVEL logger request=<request_id> user=<user_id>: event key=value ...
```

Пример:

```
[2026-08-05 14:22:31,004] INFO ecosystem.workflow request=8f3c1d... user=12: workflow.transition_completed action=send_to_ko act_id=417 actor_user_id=12 previous_status=CREATED_OTK next_status=KO_REVIEW duration_ms=41.2 outcome=ok
```

Правила формата обеспечивает `ecosystem.logging_utils.log_event()`:

- одна логическая запись — одна строка;
- порядок полей детерминированный (тот, в котором они переданы);
- переводы строк и управляющие символы экранируются;
- `UUID`, числа, `bool` и `Enum` приводятся к безопасному виду;
- вложенный payload запрещён: словарь, модель или форма записываются как
  `<unsupported:dict>`, а не сериализуются.

Записи уровня `ERROR` сохраняют полный stack trace — он и есть их ценность.
Значения внутри трассировки при этом проходят фильтр редактирования.

## 3. `request_id`

Каждый обычный запрос получает новый UUID. Он:

- генерируется приложением; входящий заголовок `X-Request-ID` **не принимается**
  (клиент мог бы намеренно повторить чужой идентификатор и сделать журнал
  бесполезным именно тогда, когда он нужен);
- кладётся в `request.request_id` и в `ContextVar`;
- попадает в каждую строку журнала, записанную во время этого запроса, включая
  строки из сервисов актов, задач и почты;
- возвращается клиенту в заголовке ответа `X-Request-ID`;
- очищается в `finally`, поэтому следующий запрос никогда не наследует чужой
  контекст. `ContextVar` — единственный механизм, корректно работающий под
  ASGI, где один поток обслуживает много одновременных запросов.

Пользователь называет `X-Request-ID` из ответа (или из сообщения об ошибке), и
администратор находит по нему всю цепочку — см. раздел 8.

## 4. Что логируется и что нет

### Обычные HTTP-запросы

На уровне INFO записываются только `POST`, `PUT`, `PATCH`, `DELETE`.
`GET` и `HEAD` записываются, **только** если запрос:

- медленнее `LOG_SLOW_REQUEST_MS` (по умолчанию 2000 мс) — `outcome=slow`;
- завершился 4xx (`WARNING`) или 5xx (`ERROR`);
- вызвал исключение — тогда пишется `http.request_failed` со stack trace.

Обычный быстрый успешный `GET` не записывается вообще. Это осознанное
ограничение объёма: журнал, в котором есть каждый `GET`, никто не читает, а
ротация вытесняет из него ту единственную ошибку, ради которой он ведётся.

Не записываются никогда: `/health/live/`, `/health/ready/` (если не включён
`LOG_HEALTH_REQUESTS`), static, media, favicon.

Длительный SSE-поток `/realtime/events/` исключён из правила медленного
запроса: он открыт минутами по своей природе. Его жизненный цикл пишет logger
`realtime` по `connection_id`.

### Поля запроса

Записываются: метод, имя маршрута (не путь с параметрами), HTTP-статус,
`duration_ms`, `request_id`, `user_id`, `outcome`.

**Не записываются**: query string, тело запроса, cookies, заголовок
`Authorization`, CSRF-токен, ключ сессии, IP-адрес (до отдельного решения
ИТ/ИБ), имя пользователя и email.

### Бизнес-операции

| Событие | Безопасные поля |
| --- | --- |
| `workflow.transition_started` / `_completed` / `_rejected` / `_failed` | `action`, `act_id`, `actor_user_id`, `previous_status`, `next_status`, `duration_ms`, `outcome` |
| `task.created`, `task.assignees_replaced`, `task.completed`, `task.operation_rejected`, `task.operation_failed` | `task_id`, `act_id`, `actor_user_id`, `assignee_count`, `previous_status`, `next_status`, `duration_ms` |
| `email.worker_started` / `_completed`, `email.delivery_sent` / `_retry_scheduled` / `_failed` / `_abandoned` | `delivery_id`, `notification_id`, `recipient_user_id`, `attempt_number`, `duration_ms`, `error_type`, `outcome`, итоговые counts |
| `realtime.connection_opened` / `_closed` / `_cancelled`, `realtime.redis_disconnected`, `realtime.publish_failed`, `realtime.slow_publish`, `realtime.slow_sync`, `realtime.invalid_message` | `connection_id`, `user_id`, `event_type`, `channel_count`, `duration_ms`, `reason`, `event_count` |
| `attachment.uploaded`, `attachment.downloaded`, `attachment.access_denied`, `attachment.storage_failed` | `attachment_id`, `act_id`, `user_id`, `size_bytes`, `operation`, `outcome` |

### Запрещённые данные

Ни при каких условиях в журнал не попадают:

- `SECRET_KEY`, `DB_PASSWORD`, `EMAIL_HOST_PASSWORD`, Redis URL с учётными
  данными, любые URL с credentials;
- cookies, CSRF-токены, ключи сессий, заголовки `Authorization` и `Cookie`;
- описание дефекта, комментарий возврата, текст решения КО, корневая причина,
  содержание мероприятий, данные заказчика и партии;
- текст задачи и `execution_comment`, имена и email исполнителей;
- адрес получателя письма, тема, тело, полный SMTP-ответ;
- сериализованное событие real-time, notification payload, HTML-фрагменты;
- оригинальное имя вложения, путь на диске, содержимое, MIME-метаданные;
- имена пользователей.

Последний рубеж — `SensitiveValueRedactionFilter`. Он применяется ко **всем**
обработчикам, поэтому маскирует секрет, попавший в запись откуда угодно,
включая внутренние сообщения Django и сторонних библиотек. Хост в сообщении
остаётся видимым — именно он делает сообщение диагностическим.

**Журнал — это не бизнес-аудит.** Историей действий остаётся `ActHistory`;
логи предназначены для диагностики и могут быть ротированы и удалены.
Отдельной модели `AuditLog` в проекте нет и добавлять её не следует.

## 5. Переменные окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | общий уровень |
| `REALTIME_LOG_LEVEL` | значение `LOG_LEVEL` | уровень logger'а `realtime` |
| `LOG_TO_FILE` | `true` при `APP_ENV=production`, иначе `false` | файловый журнал |
| `LOG_TO_CONSOLE` | `true` везде | вывод в stdout |
| `LOG_FILE_PATH` | `BASE_DIR/logs/application.log` | путь; в production — абсолютный, вне репозитория |
| `LOG_FILE_MAX_BYTES` | `20971520` (20 МБ) | размер одного файла |
| `LOG_FILE_BACKUP_COUNT` | `10` | число архивных копий |
| `LOG_SLOW_REQUEST_MS` | `2000` | порог медленного запроса |
| `LOG_MUTATING_REQUESTS` | `true` | писать POST/PUT/PATCH/DELETE |
| `LOG_HEALTH_REQUESTS` | `false` | писать health-пробы (для диагностики) |
| `APP_RELEASE` | пусто | безопасная метка версии или commit SHA |

Хотя бы один обработчик обязан быть включён: при `LOG_TO_FILE=false` и
`LOG_TO_CONSOLE=false` процесс отказывается стартовать — журнал, который никуда
не пишет, молча теряет единственную запись о произошедшей ошибке.

### Рекомендуемая production-конфигурация

```
LOG_LEVEL=INFO
REALTIME_LOG_LEVEL=INFO
LOG_TO_FILE=true
LOG_TO_CONSOLE=true
LOG_FILE_PATH=/var/log/quality/application.log
LOG_FILE_MAX_BYTES=20971520
LOG_FILE_BACKUP_COUNT=12
LOG_SLOW_REQUEST_MS=2000
LOG_MUTATING_REQUESTS=true
LOG_HEALTH_REQUESTS=false
APP_RELEASE=<версия или короткий commit SHA>
```

Каталог создаётся заранее и принадлежит служебной учётной записи приложения.
**Файл журнала не должен находиться внутри `STATIC_ROOT` или `MEDIA_ROOT`**:
`STATIC_ROOT` раздаётся публично, а `MEDIA_ROOT` содержит вложения актов.
Совпадение — блокирующая ошибка `ecosystem.E025`.

## 6. Проверка настройки

```powershell
python manage.py check           # включает проверки логирования
python manage.py check_logging   # только чтение: handlers, уровень, ротация, путь
python manage.py check_logging --write-probe
```

`check_logging` показывает включённые обработчики, уровень, параметры ротации и
готовность пути. Полный путь печатается локальному оператору, но **не**
попадает в JSON-отчёт (`--json-report`): это инфраструктурная деталь.

`--write-probe` записывает одну обычную строку `logging.probe` уровня INFO и
сообщает, изменился ли файл. Он намеренно **не** создаёт искусственный `ERROR`:
поддельная ошибка в рабочем журнале — верный способ приучить администратора не
доверять файлу. База данных при этом не изменяется.

Проверки конфигурации, выполняемые обычным `manage.py check`:

| Идентификатор | Условие |
| --- | --- |
| `E022` | не включён ни один обработчик |
| `E023` | `LOG_FILE_MAX_BYTES <= 0` |
| `E024` | `LOG_FILE_BACKUP_COUNT <= 0` |
| `E025` | путь журнала внутри `STATIC_ROOT` или `MEDIA_ROOT` |
| `E026` | относительный путь при `APP_ENV=production` |
| `E027` / `W007` | каталог или файл недоступен для записи (в production — ошибка) |

Раздел логирования входит и в `check_production_readiness` — отдельными
проверками `log_handlers`, `log_rotation`, `log_path`, без повторов.

## 7. Ротация, объём и срок хранения

`RotatingFileHandler` переключает файл по достижении `LOG_FILE_MAX_BYTES` и
хранит `LOG_FILE_BACKUP_COUNT` архивных копий (`application.log.1`, `.2`, …).
При рекомендуемых значениях верхняя граница занимаемого места —
примерно 20 МБ × 13 ≈ 260 МБ.

Свободное место контролируется отдельно: приложение не следит за диском.
Разместите журнал на разделе, где его рост не может вытеснить базу данных или
`MEDIA_ROOT`, и включите мониторинг свободного места средствами ИТ-службы.

Срок хранения определяется ротацией: старейшая копия удаляется автоматически.
Если требуется хранить журналы дольше, их следует копировать во внешнее
хранилище средствами ОС — приложение архивов не накапливает.

Объём удерживается правилами из раздела 4: не логируется каждый heartbeat, не
логируется каждый успешный быстрый `/realtime/sync/` (он на DEBUG), не
логируется каждое открытие fragment endpoint, а успешные повторяющиеся события
агрегируются (worker пишет одну итоговую строку на запуск, а не строку на
доставку).

## 8. Порядок расследования инцидента

1. Получите от пользователя `X-Request-ID` (заголовок ответа) либо время и
   действие.
2. Найдите в журнале все строки с этим `request_id`:

   ```powershell
   Select-String -Path C:\var\log\quality\application.log* -Pattern "request=8f3c1d"
   ```

   ```bash
   grep -h "request=8f3c1d" /var/log/quality/application.log*
   ```

3. Одна цепочка обычно выглядит так: `http.request` → `workflow.*` или
   `task.*` → `realtime.*`. Все они несут один `request_id`.
4. Для отказа смотрите `outcome`: `rejected` — обычный отказ по правам или
   статусу; `failed` — техническая ошибка, рядом будет stack trace.
5. Почтовые проблемы ищите по `delivery_id` в logger'е `notifications.email`;
   `error_type` называет класс исключения, полный SMTP-ответ намеренно не
   сохраняется.
6. Проблемы real-time ищите по `connection_id` в logger'е `realtime`.

Бизнес-историю действий (кто и что сделал с актом) смотрите не в журнале, а на
вкладке «История акта» — это и есть аудит.

## 9. Один и несколько процессов Uvicorn

**Пилот рассчитан на один worker.** Стандартный `RotatingFileHandler` при этом
полностью корректен.

Несколько процессов Uvicorn, независимо ротирующих **один общий файл**,
перемешают записи и потеряют часть строк: каждый процесс держит собственный
дескриптор и выполняет переименование, не зная о других. Поэтому при более чем
одном worker'е:

- либо оставьте только консоль (`LOG_TO_FILE=false`, `LOG_TO_CONSOLE=true`) и
  поручите сбор и ротацию системе (`systemd` + `journald`, Windows Service +
  внешний сборщик, драйвер логов контейнера);
- либо выдайте каждому процессу собственный `LOG_FILE_PATH`;
- либо выполняйте ротацию внешним механизмом (`logrotate` с `copytruncate`),
  задав `LOG_FILE_BACKUP_COUNT` достаточно большим, чтобы приложение не
  ротировало файл само.

Многопроцессная сторонняя библиотека логирования в проект не добавляется.

Завершение процесса — ответственность process manager. Собственный shutdown
hook не добавлен намеренно: гарантировать его выполнение под Uvicorn нельзя, а
не выполнившийся hook хуже отсутствующего.

## 10. Передача логов ИТ-службе

Перед передачей файла во внешний тикет или подрядчику:

- журнал уже не содержит секретов, паролей, токенов, cookie, адресов
  получателей и текстов пользователей — это обеспечивают фильтр редактирования
  и правила раздела 4;
- в нём остаются идентификаторы объектов (`act_id`, `task_id`, `user_id`) и
  имя хоста Redis/SMTP в диагностических сообщениях. Это внутренние
  идентификаторы, но не персональные данные и не учётные данные;
- полный путь к файлу и `APP_RELEASE` — инфраструктурные сведения; в JSON-отчёт
  `check_logging` путь не включается.

Если ИТ-служба разворачивает централизованный сбор, подключать его следует к
**консольному** потоку: он уже содержит те же записи в том же формате, и для
этого не требуется менять ни настройки приложения, ни бизнес-код.
