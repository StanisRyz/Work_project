# Эксплуатация

Документ для ИТ-службы: операционный журнал, поиск инцидента, health, email
worker, диагностика Redis и SSE, основные команды.

## 1. Операционный журнал

**Основной носитель — ротируемый текстовый файл UTF-8.** Он лежит на сервере,
читается человеком без внешних инструментов и не требует ни одной
дополнительной службы (`LOG_TO_FILE`, по умолчанию `true` при
`APP_ENV=production`).

Консольный вывод остаётся включённым рядом (`LOG_TO_CONSOLE`, по умолчанию
`true` везде): его собирает process manager, и через него позже подключается
централизованный сбор без изменения бизнес-кода. Хотя бы один обработчик обязан
быть включён — процесс с обоими выключенными не стартует.

Используется только стандартный `logging` из Python. ELK, Loki, Sentry, Graylog
и другие внешние платформы не подключаются.

### Категории

| Logger | Что записывает |
| --- | --- |
| `ecosystem.request` | одна строка на изменяющий, медленный или неуспешный HTTP-запрос |
| `ecosystem.startup` | `application.started` при запуске процесса, `logging.probe` |
| `ecosystem.workflow` | переходы актов и операции с задачами |
| `ecosystem.attachments` | загрузка, скачивание, отказ в доступе, ошибка хранения |
| `notifications.email` | запуск и итог worker'а, отправка, retry, отказ |
| `realtime` | жизненный цикл SSE, публикация в Redis, медленная сверка |
| `deployment` | health-пробы и readiness |
| `maintenance` | инструменты переноса данных |
| `django.request`, `django.security` | необработанные исключения, 4xx/5xx, CSRF, `Host` |

Уровень задаётся `LOG_LEVEL`, для `realtime` — отдельно `REALTIME_LOG_LEVEL`.

### Формат строки

```
[timestamp] LEVEL logger request=<request_id> user=<user_id>: event key=value ...
```

```
[2026-08-05 14:22:31,004] INFO ecosystem.workflow request=8f3c1d... user=12: workflow.transition_completed action=send_to_ko act_id=417 actor_user_id=12 previous_status=CREATED_OTK next_status=KO_REVIEW duration_ms=41.2 outcome=ok
```

Формат обеспечивает `ecosystem.logging_utils.log_event()`: одна логическая
запись — одна строка, детерминированный порядок полей, экранированные
управляющие символы, только скаляры. Словарь, модель или форма записываются как
`<unsupported:…>`, а не сериализуются. Записи `ERROR` сохраняют полный stack
trace — он и есть их ценность.

### Что не логируется никогда

- `SECRET_KEY`, `DB_PASSWORD`, `EMAIL_HOST_PASSWORD`, Redis URL с учётными
  данными, любые URL с credentials;
- cookies, CSRF-токены, ключи сессий, заголовки `Authorization` и `Cookie`,
  query string и тело запроса;
- пользовательские тексты: описание дефекта, комментарий возврата, решение КО,
  корневая причина, содержание мероприятий, текст задачи и результат
  выполнения;
- данные заказчика и партии, имена пользователей, email-адреса, тема и тело
  письма, полный SMTP-ответ;
- сериализованное real-time событие, имена каналов Redis, HTML-фрагменты;
- имя вложения, путь на диске, содержимое и MIME-метаданные.

Записываются идентификаторы, коды, счётчики, `duration_ms` и `outcome`.
Последний рубеж — `SensitiveValueRedactionFilter`, навешенный на **все**
обработчики; `SafeFormatter` применяет его повторно после форматирования,
поэтому отрендеренная трассировка не может протащить секрет мимо фильтров.

**Журнал — не бизнес-аудит.** Историей действий остаётся `ActHistoryEvent`
(вкладка «История акта»); логи предназначены для диагностики и могут быть
ротированы и удалены. Отдельной модели `AuditLog` в проекте нет.

### Объём

INFO пишется для `POST`/`PUT`/`PATCH`/`DELETE`. `GET` и `HEAD` попадают в
журнал, только если запрос медленнее `LOG_SLOW_REQUEST_MS` (по умолчанию
2000 мс), завершился 4xx/5xx или вызвал исключение. Обычный быстрый успешный
`GET` не записывается: журнал, в котором есть каждый `GET`, никто не читает, а
ротация вытесняет из него ту единственную ошибку, ради которой он ведётся.

Исключены: `/health/live/`, `/health/ready/` (пока не включён
`LOG_HEALTH_REQUESTS`), static, media, favicon. Долгий SSE-поток
`/realtime/events/` исключён из правила медленного запроса — он открыт минутами
по своей природе, а его жизненный цикл пишет logger `realtime` по
`connection_id`.

Не логируются heartbeat, успешная быстрая сверка и успешная публикация в Redis
(они на `DEBUG`), а повторяющиеся успешные события агрегируются: email worker
пишет одну итоговую строку на запуск, а не строку на доставку.

## 2. `request_id`

Каждый обычный запрос получает новый UUID. Он:

- генерируется приложением. Входящий заголовок `X-Request-ID` **не
  принимается**: клиент мог бы намеренно повторить чужой идентификатор и
  сделать журнал бесполезным именно тогда, когда он нужен;
- кладётся в `request.request_id` и в `ContextVar`;
- попадает в каждую строку, записанную во время этого запроса, включая строки
  из сервисов актов, задач и почты;
- возвращается клиенту в заголовке ответа `X-Request-ID`;
- очищается в `finally`, поэтому следующий запрос не наследует чужой контекст.
  `ContextVar` — единственный механизм, корректный под ASGI, где один поток
  обслуживает много одновременных запросов.

`RequestLoggingMiddleware` стоит **после** `AuthenticationMiddleware`: ему нужен
разрешимый `request.user`, и он должен обернуть вьюху, чтобы измерить запрос и
перехватить исключение на выходе.

## 3. Порядок расследования инцидента

1. Получите от пользователя `X-Request-ID` из ответа либо время и действие.
2. Найдите все строки с этим идентификатором:

   ```powershell
   Select-String -Path C:\var\log\quality\application.log* -Pattern "request=8f3c1d"
   ```

   ```bash
   grep -h "request=8f3c1d" /var/log/quality/application.log*
   ```

3. Обычная цепочка: `http.request` → `workflow.*` или `task.*` → `realtime.*`.
   У всех один `request_id`.
4. Смотрите `outcome`: `rejected` — обычный отказ по правам или статусу;
   `failed` — техническая ошибка, рядом будет stack trace.
5. Почтовые проблемы — по `delivery_id` в logger'е `notifications.email`;
   `error_type` называет класс исключения, полный SMTP-ответ не сохраняется.
6. Проблемы real-time — по `connection_id` в logger'е `realtime`.

Бизнес-историю («кто и что сделал с актом») смотрите на вкладке «История акта»,
а не в журнале.

## 4. `check_logging`

```powershell
python manage.py check                     # включает проверки логирования
python manage.py check_logging             # только чтение
python manage.py check_logging --write-probe
```

`check_logging` показывает включённые обработчики, уровень, параметры ротации и
готовность пути. Полный путь печатается локальному оператору, но **не** попадает
в JSON-отчёт: это инфраструктурная деталь.

`--write-probe` записывает одну обычную строку `logging.probe` уровня INFO и
сообщает, изменился ли файл. Он намеренно **не** создаёт искусственный `ERROR`:
поддельная ошибка в рабочем журнале — верный способ приучить администратора не
доверять файлу. База данных при этом не изменяется.

Конфигурацию логирования проверяют и системные проверки (`ecosystem.E022`–`E027`,
`W007`): отсутствие обработчиков, некорректная ротация, журнал внутри
`STATIC_ROOT` или `MEDIA_ROOT`, относительный путь в production, недоступный
для записи каталог. Тот же раздел входит в `check_production_readiness`.

## 5. Ротация и место на диске

`RotatingFileHandler` переключает файл по достижении `LOG_FILE_MAX_BYTES` и
хранит `LOG_FILE_BACKUP_COUNT` архивных копий (`application.log.1`, `.2`, …).
При значениях по умолчанию верхняя граница — примерно 20 МБ × 11 ≈ 220 МБ.

Свободное место контролируется отдельно: приложение за диском не следит.
Размещайте журнал на разделе, где его рост не может вытеснить базу данных или
`MEDIA_ROOT`. **Файл журнала не должен находиться внутри `STATIC_ROOT` или
`MEDIA_ROOT`**: первый раздаётся публично, второй содержит вложения актов.

Срок хранения определяется ротацией — старейшая копия удаляется автоматически.
Для более долгого хранения копируйте файлы во внешнее хранилище средствами ОС.

### Несколько процессов Uvicorn

**Пилот рассчитан на один worker**, и стандартный `RotatingFileHandler` при
этом полностью корректен.

Несколько процессов, независимо ротирующих **один общий файл**, перемешают
записи и потеряют часть строк: каждый процесс держит собственный дескриптор и
выполняет переименование, не зная о других. Поэтому при более чем одном
worker'е выберите один из вариантов:

- оставить только консоль (`LOG_TO_FILE=false`, `LOG_TO_CONSOLE=true`) и
  поручить сбор и ротацию системе (systemd + journald, служба Windows +
  внешний сборщик, драйвер логов контейнера);
- выдать каждому процессу собственный `LOG_FILE_PATH`;
- выполнять ротацию внешним механизмом (`logrotate` с `copytruncate`), задав
  `LOG_FILE_BACKUP_COUNT` достаточно большим, чтобы приложение не ротировало
  файл само.

Многопроцессная сторонняя библиотека логирования не добавляется. Завершение
процесса — ответственность process manager: собственный shutdown hook не
добавлен намеренно, гарантировать его выполнение под Uvicorn нельзя.

## 6. Health и readiness

| Endpoint | Ожидаемый ответ |
| --- | --- |
| `GET /health/live/` | `200 {"status": "ok"}` — процесс жив, зависимости не проверяются |
| `GET /health/ready/` | `200 {"status": "ready"}` либо `503 {"status": "unavailable"}` |

Readiness не описывает инфраструктуру в теле ответа: причина отказа пишется в
logger `deployment`. Проверяются `SELECT 1`, отсутствие неприменённых миграций,
Redis PING (только при real-time на Redis-backend), `MEDIA_ROOT` и
`STATIC_ROOT`.

Liveness намеренно не зависит от базы: иначе недоступность PostgreSQL
заставила бы process manager перезапускать здоровые процессы по кругу.

## 7. Email worker

Отдельное задание раз в минуту:

```powershell
python manage.py process_notification_deliveries --batch-size 100
```

Диагностика:

- статусы доставок — `pending`, `processing`, `sent`, `failed`, `skipped`.
  `skipped` означает выключенные уведомления или отсутствующий адрес
  получателя, а не сбой;
- worker пишет `email.worker_started` и `email.worker_completed` с итоговыми
  счётчиками, а также `email.delivery_sent`, `_retry_scheduled`, `_failed`,
  `_abandoned` по каждой проблемной доставке;
- зависшие `processing` восстанавливаются следующим запуском по истечении
  `EMAIL_NOTIFICATION_PROCESSING_TIMEOUT_SECONDS`;
- пересекающиеся запуски безопасны: перевод `pending → processing` атомарен, и
  право отправки получает только один процесс;
- недоступный SMTP **не влияет** на действия пользователей и внутренние
  уведомления: письмо просто откладывается по расписанию повторов.

Проверка планировщика:

```bash
systemctl status quality-email-queue.timer
journalctl -u quality-email-queue.service -n 100 --no-pager
```

```powershell
Get-ScheduledTaskInfo -TaskName 'QualityEcosystem-EmailQueue'
Get-WinEvent -LogName 'Microsoft-Windows-TaskScheduler/Operational' -MaxEvents 100
```

## 8. Диагностика Redis и SSE

```powershell
python manage.py check_realtime_transport
python manage.py check_sse_db_connections --label before --json-report before.json
```

`check_realtime_transport` выполняет настоящий PING и round trip публикации
через одноразовый диагностический канал и печатает адрес Redis **без учётных
данных**. Readiness-проба его не заменяет: она делает только PING, а доставка
может не работать, например при разных `REALTIME_CHANNEL_PREFIX` у двух
приложений на одном Redis.

`check_sse_db_connections` показывает через `pg_stat_activity`, не удерживают
ли открытые SSE-потоки соединения с базой в состоянии `idle in transaction`.
Ожидание: 20–50 потоков **не** дают 20–50 таких соединений, а после закрытия
число возвращается к исходному.

За чем следить в logger'е `realtime`:

| Событие | Что означает |
| --- | --- |
| рост `realtime.redis_disconnected` | проблема сети или самого Redis |
| рост `realtime.slow_sync` | агрегаты сверки упираются в размер таблиц |
| `realtime.invalid_message` | несовместимые версии приложения на одном Redis |
| `realtime.publish_failed` | событие не ушло в транспорт; бизнес-операция уже зафиксирована и не пострадала |
| `realtime.stream_refused` | Redis не ответил на preflight, клиент получил 503 |
| `realtime.event_oversized` | событие превысило `REALTIME_MAX_EVENT_BYTES` и было отброшено |

## 10. Типовые действия при сбое

| Симптом | Что делать |
| --- | --- |
| `/health/ready/` отдаёт 503 | причина в logger'е `deployment`: база, неприменённые миграции, Redis, `MEDIA_ROOT` или `STATIC_ROOT` |
| Страницы не открываются, процесс не стартует | конфигурация отклонена при импорте настроек — сообщение в консоли process manager; значение секрета в нём не печатается |
| Интерфейс не обновляется живьём | проверьте ASGI (не WSGI), `REALTIME_ENABLED`, `check_realtime_transport`, буферизацию на прокси; данные при этом не теряются — обновление вернётся после сверки |
| В журнале растут `publish_failed` | Redis недоступен; бизнес-операции сохраняются, интерфейс досчитывается сверкой |
| Письма не уходят | проверьте, что задание планировщика включено и `EMAIL_NOTIFICATIONS_ENABLED=true`; ищите `delivery_id` в `notifications.email` |
| Доставки в статусе `skipped` | уведомления были выключены или у получателя нет адреса; они намеренно не отправляются задним числом |
| Журнал не пишется | `check_logging --write-probe`; проверьте права на каталог и что путь абсолютный |
| Записи в журнале перемешаны | запущено несколько Uvicorn workers на один файл — см. раздел 5 |
| Медленные переходы актов | ищите `workflow.transition_*` с большим `duration_ms` и проверьте таймауты PostgreSQL |
| Нужно передать журнал во внешний тикет | секретов и пользовательских текстов в нём нет; остаются идентификаторы объектов и имена хостов Redis/SMTP в диагностических сообщениях |

Восстановление данных из резервной копии — в
[backup_restore.md](backup_restore.md). Требования к среде — в
[deployment.md](deployment.md).
