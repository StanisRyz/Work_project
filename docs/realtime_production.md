# Развёртывание real-time: требования к среде

Документ описывает, **что должна обеспечивать среда**, чтобы real-time работал
в пилотной эксплуатации. Он намеренно не привязан к конкретной ОС и не содержит
готовых конфигураций: сервер ещё не выбран. Production-развёртывание этим
патчем не выполняется.

## 1. Django запускается только как ASGI

SSE — длительное соединение. WSGI его не держит: `runserver` и любой
WSGI-сервер закроют поток или заблокируют воркер.

- `ASGI_APPLICATION = 'ecosystem.asgi.application'` (уже задано);
- приложение запускается ASGI-сервером, например
  `uvicorn ecosystem.asgi:application`;
- число воркеров подбирается так, чтобы одно долгоживущее соединение на
  пользователя не занимало воркер целиком — asyncio-воркер держит тысячи
  соединений, но каждый воркер имеет собственный лимит файловых дескрипторов;
- обычные страницы могут по-прежнему обслуживаться тем же ASGI-процессом.

## 2. Redis — отдельная закрытая служба

- Redis работает как самостоятельная служба, а не внутри процесса приложения;
- слушает только внутренний интерфейс или закрыт сетевыми правилами: снаружи
  порт недоступен;
- при аутентификации используется `rediss://` либо доверенная внутренняя сеть;
- Redis используется **только как транспорт**: события не хранятся, не
  переигрываются и не подтверждаются. Потеря сообщения означает пропущенное
  обновление интерфейса, а не потерю данных — состояние восстанавливается через
  `/realtime/sync/`;
- persistence Redis для real-time не требуется; при перезапуске сервера все
  клиенты просто переподключаются и выполняют сверку;
- отдельная база (`/0`, `/1`, …) или отдельный `REALTIME_CHANNEL_PREFIX` на
  каждую среду, чтобы тестовая и рабочая не пересекались.

## 3. Reverse proxy и `text/event-stream`

Прокси обязан пропускать поток без накопления:

- **буферизация выключена** для `/realtime/events/`. Приложение уже отдаёт
  `X-Accel-Buffering: no`, но прокси должен это уважать либо иметь явную
  настройку;
- **кэширование выключено**: ответ уже помечен
  `Cache-Control: no-cache, no-store, no-transform`, сжатие и трансформация
  ответа недопустимы;
- **таймауты чтения больше heartbeat**: heartbeat по умолчанию 25 с, значит
  read/idle timeout прокси должен быть заметно больше (например 120 с) и
  больше `REALTIME_MAX_CONNECTION_SECONDS` быть не обязан — поток и так
  закрывается сам;
- HTTP/1.1 или HTTP/2 без принудительного закрытия keep-alive;
- лимит одновременных соединений на upstream должен покрывать
  «пользователи × вкладки-лидеры» (см. раздел 6).

## 4. HTTPS и cookies

- внешний доступ только по HTTPS: SSE передаёт события пользователя;
- `SESSION_COOKIE_SECURE = True` и `CSRF_COOKIE_SECURE = True` в
  production-настройках;
- `SESSION_COOKIE_SAMESITE = 'Lax'` достаточно: EventSource обращается к
  собственному origin;
- при истечении сессии сервер отвечает `401`, клиент останавливается и не
  создаёт бесконечный цикл переподключений.

## 5. Перезапуски

- **Graceful restart ASGI.** При перезапуске все SSE-соединения закрываются.
  Это штатная ситуация: браузер переподключается через объявленный `retry`, а
  первый успешный `open` выполняет полную сверку через `/realtime/sync/`.
  Дренаж соединений перед остановкой желателен, но не обязателен.
- **Перезапуск Redis.** Публикация во время недоступности Redis теряется —
  это допустимо: сохранённые бизнес-операции не страдают
  (`REALTIME_FAIL_SILENTLY`), а клиенты досчитывают состояние сверкой.
- **Максимальное время соединения.** `REALTIME_MAX_CONNECTION_SECONDS`
  (по умолчанию 900 с) заставляет поток закрыться самостоятельно, чтобы каждое
  новое соединение заново прошло аутентификацию и проверку прав. Это же
  ограничивает время жизни соединения на прокси.

## 6. Ожидаемое число соединений

При доступном `BroadcastChannel` активна **одна** SSE-подписка на пользователя,
а не на вкладку: вкладка-лидер держит соединение и раздаёт события остальным.

```
соединений ≈ активные пользователи × (1 + доля браузеров без BroadcastChannel)
```

Для пилота порядка 50 пользователей это десятки соединений, а не сотни.
Планировать стоит с запасом ×2 на переподключения и на вкладки в приватном
режиме, где `localStorage`/`BroadcastChannel` могут быть недоступны и каждая
вкладка работает самостоятельно.

## 7. Проверка после запуска

Сразу после развёртывания:

```powershell
python manage.py check
python manage.py check_realtime_transport
```

`check` включает системные проверки real-time: включённый real-time с Noop
publisher, отсутствующий или некорректный Redis URL, недопустимая схема,
отсутствующий `ASGI_APPLICATION`, heartbeat не меньше времени жизни
соединения, некорректные интервалы polling и leader lease, недопустимый
префикс каналов. При `DEBUG=False` опасные комбинации — ошибки, а не
предупреждения.

`check_realtime_transport` выполняет реальный PING и round trip публикации
через одноразовый диагностический канал и печатает адрес Redis **без учётных
данных**.

Затем — ручная проверка: открыть две вкладки под одним пользователем, второй
учётной записью выполнить действие, создающее уведомление, и убедиться, что
счётчик и меню обновляются без F5.

## 8. Пилотная нагрузочная проверка

```powershell
$env:REALTIME_SMOKE_PASSWORD = "<пароль тестовой учётной записи>"
python scripts/realtime_load_smoke.py --base-url http://127.0.0.1:8000 `
    --username smoke_user --connections 50 --seconds 1800
```

Скрипт отказывается работать против нелокального адреса без явного
подтверждения, не хранит пароли и не читает браузерные cookie.

Минимальный профиль пилота:

- до 50 пользователей, 1–3 вкладки каждый;
- 30–60 минут непрерывно;
- в это время: создание задач, серия смен статусов актов, перезапуск Redis,
  перезапуск ASGI-сервера, закрытие вкладки-лидера;
- ожидаемый результат: соединения восстанавливаются, счётчики и списки
  сходятся с базой после каждой сверки, ошибок в логах уровня ERROR нет.

## 9. Логи

Приложение пишет структурированные записи в logger `realtime`:
`realtime.connection_opened`, `connection_closed`, `connection_cancelled`,
`redis_disconnected`, `sync_completed`, `sync_slow`, `invalid_message`. В них
есть идентификатор соединения, идентификатор пользователя, длительность,
причина закрытия, число событий и время сверки — и нет payload, текстов,
email и учётных данных.

Стоит следить за:

- ростом `redis_disconnected` — проблема сети или самого Redis;
- ростом `sync_slow` — агрегаты сверки упираются в размер таблиц;
- `invalid_message` — несовместимые версии приложения на одном Redis.

## 10. Чего этот документ не делает

- не выбирает ОС, дистрибутив и сервер;
- не содержит готовых конфигураций reverse proxy и systemd/служб Windows;
- не разворачивает Redis и не настраивает его аутентификацию;
- не содержит реальных секретов, паролей и адресов;
- не выполняет production-развёртывание — это отдельный согласованный этап.
