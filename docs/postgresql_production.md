# PostgreSQL в production: роли и права

Документ описывает **рекомендуемую модель ролей**. Он намеренно не содержит
готовых SQL-команд с реальными именами, паролями и адресами: их формирует
администратор PostgreSQL в своей среде, и они никогда не попадают в Git.
Установка PostgreSQL, создание ролей и настройка сервера этим этапом не
выполняются.

## 1. Три роли

| Роль | Назначение | Когда используется |
| --- | --- | --- |
| `quality_owner` | владелец базы и схемы | миграции, изменение структуры |
| `quality_app` | рабочая роль приложения | штатная работа, `DB_USER` |
| `quality_backup` | чтение для резервного копирования | `pg_dump` |

### `quality_owner`

Владеет базой и объектами схемы. Используется **только** для
`python manage.py migrate` и других операций, изменяющих структуру. Не
используется приложением в штатной работе.

### `quality_app`

Роль, которую приложение указывает в `DB_USER`. В штатной работе ей нужны
только права на данные:

- `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицах приложения;
- `USAGE`, `SELECT`, `UPDATE` на последовательностях (нужны для генерации
  первичных ключей и `ActNumberSequence`);
- `USAGE` на схеме.

**Лишние права на схему ей не нужны**: `CREATE` на схеме, `DROP`, `ALTER`
структуры. Приложение не создаёт и не изменяет таблицы во время работы — это
делают миграции под owner-ролью. Ограничение прав означает, что ошибка или
уязвимость в коде приложения не сможет изменить структуру базы.

### `quality_backup`

Только чтение, для снятия резервных копий. Не используется приложением.

## 2. Разделение миграций и работы

Рекомендуемый порядок:

1. остановить или перевести в режим обслуживания приложение;
2. выполнить `migrate` под owner/migration ролью;
3. вернуть приложение в работу под `quality_app`.

Так рабочая роль никогда не нуждается в правах на изменение схемы.

## 3. Допустимое упрощение для первого пилота

Для первого пилота допустимо **задокументированное** временное упрощение:
одна роль, совмещающая владение и работу приложения. Это осознанный
компромисс, а не норма. Если он принят, зафиксируйте:

- что используется одна роль;
- почему (сроки, объём пилота, отсутствие выделенного DBA);
- когда планируется разделение.

Разделение ролей — обязательное условие перехода из пилота в постоянную
эксплуатацию.

## 4. Соединение

| Переменная | Рекомендация для production |
| --- | --- |
| `DB_SSLMODE` | `require` и выше; `verify-full` при наличии CA |
| `DB_APPLICATION_NAME` | значимое имя — видно в `pg_stat_activity` |
| `DB_STATEMENT_TIMEOUT_MS` | `30000` |
| `DB_LOCK_TIMEOUT_MS` | `10000` |
| `DB_IDLE_IN_TRANSACTION_TIMEOUT_MS` | `60000` |
| `DB_CONN_MAX_AGE` | `0` под ASGI |

`disable`, `allow` и `prefer` допускают незашифрованное соединение и дают
предупреждение `ecosystem.W003`. Для соединения по сети это неприемлемо.

Runtime-таймауты обязательны: без них один зависший запрос или забытая
открытая транзакция удерживают блокировки неограниченно долго, а под ASGI это
особенно заметно. Значение `0` отключает таймаут и даёт предупреждение
`ecosystem.W004`.

## 5. Число соединений

`DB_CONN_MAX_AGE=0` остаётся рекомендуемым значением: длительное SSE-соединение
не должно удерживать соединение с базой на всё своё время жизни. Проверить это
на конкретном сервере можно так:

```powershell
python manage.py check_sse_db_connections --label before --json-report before.json
# запустить нагрузочную проверку, затем --label during, после остановки --label after
```

Ожидаемая гарантия: 20–50 открытых SSE-потоков **не** создают 20–50 соединений
в состоянии `idle in transaction`, а после закрытия число возвращается к
исходному. Persistent connections, встроенный пул и PgBouncer добавляются
только по результатам такого измерения — см.
[производительность](realtime_performance.md).

`max_connections` сервера должен покрывать: рабочие процессы ASGI × их
параллелизм + миграции + резервное копирование + запас на переподключения.

## 6. Что этот документ не делает

- не устанавливает PostgreSQL и не настраивает `postgresql.conf`/`pg_hba.conf`;
- не создаёт роли и не выдаёт права — только рекомендует модель;
- не содержит реальных имён, адресов, паролей и SQL-скриптов;
- не настраивает репликацию, отказоустойчивость и мониторинг;
- не использует PgBouncer.
