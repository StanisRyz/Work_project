# Единая цифровая экосистема управления качеством

Веб-система для работы с актами о качестве (АОК) на производстве: акт проходит
маршрут ОТК → КО → ТО → ОТК, а утверждённые корректирующие мероприятия
превращаются в задачи с исполнителями и сроками. Роль пользователя определяет,
какие акты он видит и какие действия ему доступны.

## Что уже работает

**Навигация.** Меню в верхней панели двухуровневое: категория «Качество»
(«Акты», «Задачи», «Протоколы») и категория «Калькуляторы» («Калькулятор времени
навивки», «Калькулятор рубки пластин»). Категории раскрываются по клику,
одновременно открыт только один список. Пункт «Документация» — прямая ссылка
без подменю.

**Акты.** Создание акта с данными акта и произвольным числом дефектов. Номер
акта вводит пользователь: до 5 любых символов, из которых сервер собирает
итоговый `АОК-{текущий год}-{суффикс, дополненный нулями до 5 символов}`
(`34` → `АОК-2026-00034`, `35/1` → `АОК-2026-035/1`). Номер — это бизнес-
идентификатор, он не обязан быть уникальным; уникален только внутренний
`Act.pk`. Редактирование доступно до передачи в КО;
маршрут `CREATED_OTK → KO_REVIEW → TO_ANALYSIS → OTK_REVIEW → ARCHIVED` с
возвратами на каждом этапе и обязательным комментарием возврата.

Срок рассмотрения акта — **дата создания плюс 3 рабочих дня** (только
понедельник–пятница, без праздничного календаря; день создания не считается:
понедельник → четверг, четверг → вторник, пятница → среда). Срок фиксируется
один раз при создании и не пересчитывается при редактировании дефектов.

Итоговую проверку на этапе `OTK_REVIEW` выполняет **любой активный сотрудник
ОТК**, а не только автор акта: акт возвращается в отдел, и вернуть его в ТО или
утвердить может любой из них. Акт в статусе `CREATED_OTK` остаётся рабочим
актом своего автора.

**Цеха в дефектах.** Форма дефекта зависит от выбранного цеха. «Цех МП»
собирает полный набор полей. «Цех ПиР» — только цех, номер ЗНП, вид дефекта,
дату обнаружения и количества: номер партии, операция, тип МП и описание не
запрашиваются, не сохраняются и в просмотре показываются как «—». Для ПиР
доступны только виды дефекта «Деформация», «Несоответствие размеров» и
«Другое»; ограничение проверяется на сервере. Один акт может содержать дефекты
разных цехов, каждый со своими данными: сведения о дефекте хранятся только в
дефекте, а не в акте. Поиск в реестре учитывает номер ЗНП и номер партии любого
дефекта акта.

**Решения и анализ.** Решение КО по каждому дефекту; структурированный анализ
ТО: корневые причины, корректирующие мероприятия, подразделения, сроки и
активные исполнители.

**Брак и планирование замены.** Если при передаче акта в ТО хотя бы по одному
дефекту «Цех МП» решение КО — «Запретить использование», на весь акт
автоматически создаётся одна общая задача ПДО о планировании замены (по строке
на каждый забракованный дефект: номенклатура, количество, заказ, ЗНП, партия).
Получатели определяются **по подразделению**: активные сотрудники активного
подразделения с кодом `PDO`, независимо от их роли. Дефекты «Цех ПиР» и любые
разрешающие решения задачу не создают; отсутствие ПДО не блокирует переход
акта.

**Задачи.** При утверждении акта для каждого корректирующего мероприятия
атомарно создаётся общая задача. Любой из назначенных исполнителей завершает
её один раз, обязательно указав результат выполнения. Для мероприятия с
несколькими исполнителями в «Анализе ТО» доступна галочка «Разбить задачу для
исполнителей»: по умолчанию она выключена, а включённая — создаёт при
утверждении отдельную независимую задачу каждому исполнителю. Само мероприятие
остаётся одним: в «Анализе ТО» его строка показывает прогресс («2 из 5
выполнено»), отдельные задачи видны во вкладке «Связанные мероприятия», а
печатная форма акта не меняется. Задача знает свой
источник: акт, этап обработки акта, брак по акту, согласование протокола или
задача протокола. Задачи согласования создаёт отправка протокола на согласование,
задачи по протоколу — его архивирование; задача согласования закрывается только
решением по протоколу, а не обычным «Завершить».

**Этапы акта в задачах.** Пока акт ждёт работы КО, ТО или ОТК, в реестре задач
висит одна общая задача-маршрут на этот этап, назначенная всем активным
сотрудникам нужной роли и ссылающаяся на сам акт. Переход акта закрывает
текущую задачу и открывает следующую, возврат — тоже; утверждение акта
закрывает последнюю и новой не создаёт. Такая задача не завершается кнопкой
«Завершить»: её страница ведёт в акт, где и выполняется действие. При создании
акта задача не создаётся — работа `CREATED_OTK` уже принадлежит автору.

**Вложения к задачам.** К обычной исполняемой задаче (по акту или по
протоколу) можно приложить файлы — необязательно: задача по-прежнему
завершается одним комментарием о результате и без единого вложения. Загрузка
доступна назначенному исполнителю активной задачи, скачивание — всем, кто может
читать задачу; файлы отдаются только через защищённый маршрут с проверкой прав.
Завершение задачи вложения не удаляет.

Исключение — задачи, которым вложение назначено обязательным. Автор протокола
(галочка «Обязательно вложение» у задачи протокола) и ТО (та же галочка у
корректирующего мероприятия в «Анализе ТО») могут потребовать файл заранее:
созданная задача помнит это требование, и завершить её без хотя бы одного
вложения сервер не даёт. Требование не зависит от типа, количества и автора
файла — достаточно одного. У разбитой по исполнителям задачи каждый исполнитель
выполняет требование на своей задаче; общую задачу закрывает любое вложение на
ней. В утверждённом «Анализе ТО» и в печатной форме акта требование не
показывается — оно управляет задачей, а не документом.

**Калькулятор времени навивки.** Раздел `/calculators/winding/` считает время навивки витых ленточных
магнитопроводов по согласованным формулам и ведёт общую «Проработку»: журнал
рассчитанных магнитопроводов, фактическое время партии и подтверждённые
производственные данные. Журнал хранится в базе данных приложения через
Django (в production — та же PostgreSQL, что и всё остальное), общий для всех
аутентифицированных пользователей; выбирать файл базы не требуется.

Расчёт из вкладки «Калькулятор» попадает в журнал один раз на **расчётный
случай целиком** — геометрия `d`, `D`, `b`, толщина ленты `δ` и калибровка.
Тот же магнитопровод с другой лентой или с калибровкой — отдельная строка,
повторение того же расчёта новой строки не создаёт. Строку можно добавить и
вручную прямо в «Проработке» (`d`, `D`, `b`, `δ`, калибровка и «+»): такие
строки считаются тем же расчётным движком и намеренно допускают любое число
дубликатов. Калибровка `0` означает «нет калибровки».

Для каждой строки хранятся производственные данные, время из 1С и
ответственный сотрудник. Поле «1С» принимает число или простое
арифметическое выражение **в секундах** (`4.4*75*30`), а в таблице и в
выгрузке показывается результат в часах (`2,75`).
Выгрузка в `.xlsx` доступна всегда и содержит **все** строки журнала —
подтверждённые и нет; незаполненные значения остаются пустыми ячейками.
Колонка «ВН, с/мм» — это уже рассчитанная скорость навивки, она есть и в
таблице, и в выгрузке.

Калькулятором пользуется любой аутентифицированный пользователь: расчёт,
просмотр «Проработки», поиск, обновление и выгрузка доступны всем. Изменения
журнала принадлежат ролям **ПДО** и **администратора** (плюс суперпользователь
как административный запасной вход) — они сохраняют расчёт в журнал, добавляют
строки вручную, подтверждают и правят производственные данные и удаляют строки.
ОТК, КО, ТО, мастер производства и руководитель работают с «Проработкой» только на чтение.
Подразделение «Планово-диспетчерская служба» существует отдельно и само по себе
прав не даёт.

**Калькулятор рубки пластин.** Раздел `/calculators/plate-cutting/` считает
время рубки по согласованным коэффициентам: для каждого пакета выбирается один
из 17 диапазонов длины пластины (0,74–3,55 с на пластину), указываются
количество пластин и общее количество отверстий (0,95 с за отверстие), время
пакета пересчитывается сразу при вводе. Готовый пакет подтверждается зелёной
галочкой; для изменения подтверждённой строки её сначала переводят в режим
редактирования кнопкой-карандашом. Когда подтверждены все пакеты, становится
доступно поле «Количество наборов»: оно умножает время каждой строки и общий
итог, сохраняя отдельный итог для одного набора.

Наборы хранятся в PostgreSQL и доступны для поиска и загрузки всем
аутентифицированным пользователям. Создавать, перезаписывать и удалять их могут
только ПДО, администратор и Django superuser. Сохранённый набор содержит
исходные данные пакетов, их порядок и количество одинаковых наборов; результаты
расчёта в базу не попадают и после загрузки пересчитываются текущими формулами.
Загрузка набора заменяет пакеты на экране, поэтому, если в калькуляторе уже
что-то введено, сначала спрашивается подтверждение «Заменить текущие пакеты?» —
«Отмена» возвращает к списку наборов и ничего не трогает. Пустой калькулятор
загружает набор сразу.

**Права и видимость.** Роли ОТК, КО, ТО, ПДО, мастер производства, руководителя и администратора.
Видимость проверяется на бэкенде: шаблоны используют готовый набор доступных
действий и никогда не решают вопрос доступа сами.

Роль `mas` («Мастер производства») — обычная производственная роль: акты доступны
только для чтения, собственные протоколы создаются и проходят стандартный
авторский маршрут, а назначенные обычные задачи можно завершать. MAS рассчитывает
навивку, читает, ищет и выгружает общую «Проработку», но не создаёт, не правит,
не подтверждает и не удаляет её строки. В калькуляторе рубки пластин доступны
поиск, загрузка и локальное изменение наборов, но не управление общей
библиотекой. Роль не даёт доступа в Django Admin.
Подразделение «Мастера производства» (`MAS`) и роль `mas` — разные сущности:
подразделение хранит организационные данные и само по себе не предоставляет прав.

**Рабочая страница.** После входа любой пользователь, включая администратора,
попадает сразу в реестр актов `/quality/acts/`; так же ведут себя `/` и вход без
`?next=`. Пользовательский интерфейс состоит из разделов «Акты», «Задачи», «Протоколы»
и «Калькуляторы»; управление пользователями, ролями и справочниками выполняется
через Django Admin (`/admin/`). Действия по маршруту подтверждаются модальным окном
приложения (для возвратов — с обязательным комментарием), а не диалогом
браузера.

**Адреса разделов.** Пользовательские модули живут в двухуровневой иерархии,
повторяющей навигацию: `/quality/<модуль>/` и `/calculators/<модуль>/` — сейчас
это `/quality/acts/`, `/quality/tasks/`, `/quality/protocols/`,
`/calculators/winding/` и `/calculators/plate-cutting/`. Инфраструктурные адреса (`/accounts/`,
`/notifications/`, `/realtime/`, `/health/`, `/admin/`) остаются вне неё. Прежние
плоские пути `/acts/`, `/tasks/` и `/calculator/` временно продолжают работать:
они отвечают редиректом на канонический адрес, сохраняя метод запроса.

**Уведомления.** Внутренние уведомления с дедупликацией создаются в одной
транзакции с бизнес-событием; колокольчик в шапке показывает непрочитанные.
Источником уведомления может быть акт, протокол или задача: ссылка ведёт
соответственно в акт, протокол или задачу. По протоколам приходят внутренние
уведомления о требуемом согласовании, возврате на доработку, полном
согласовании и о назначении реальной рабочей задачи, созданной по протоколу;
причина возврата в уведомление не копируется — она остаётся в согласовании и
истории протокола. Email — отдельный канал: доставки складываются в очередь в
базе и отправляются отдельной командой по таймеру, поэтому недоступный SMTP не
мешает работе. При включённом `EMAIL_NOTIFICATIONS_ENABLED` письма дублируют
важные события по всем трём источникам — актам, протоколам и назначенным
задачам, включая задачу ПДО по браку. Комментарии остаются только внутренними:
их много, отдельного требуемого действия они не несут и почтовый ящик ими не
засоряется.

**Real-time.** Redis Pub/Sub и Server-Sent Events обновляют колокольчик,
реестры, открытый акт и открытый протокол без перезагрузки. Событие сообщает только *что*
изменилось; содержимое всегда перезапрашивается обычным авторизованным
запросом. Так же синхронизируется «Проработка» в «Калькуляторе»: строка,
которую кто-то добавил, подтвердил, открыл заново или удалил, появляется у
всех открытых страниц сама, без F5 и без потери набранного в строке. Протокол
обновляется по тем же правилам: реестр, шапка, согласование, содержимое и
история приходят готовой разметкой с сервера, а редактор с несохранёнными
изменениями никогда не перетирается — вместо этого показывается предупреждение
и отключаются устаревшие действия.
Пропущенные обновления досчитывает сверка ревизий `/realtime/sync/`,
есть fallback polling и одно соединение на пользователя вместо одного на
вкладку.

**Вложения.** Файлы актов и протоколов лежат в protected media и выдаются
только через Django-вьюху с проверкой прав на каждый запрос.

**Протоколы.** Раздел `/quality/protocols/` с вкладками «В работе» и «Архив»:
любой авторизованный пользователь читает любой протокол, автор создаёт его
выбором типа (нумерация независима и переиспользуема внутри типа) и заполняет
черновик на одной странице. Страница протокола построена как документ:
несворачиваемая карточка с номером, типом, датой, автором, статусом и
индикатором этапа, а под ней раскрывающиеся секции — «Участники», «Повестка»,
«Слушали», «Задачи» и «Согласование», каждая со счётчиком в заголовке.
Содержимое сохраняется одним действием «Сохранить черновик»; вкладка «История»
показывает события протокола. Подразделение рядом с сотрудником фильтрует
список сотрудников, но никогда не стирает уже сделанный выбор: если сотрудника
перевели в другое подразделение или подразделение отключили, строка остаётся
заполненной и показывает предупреждение — заменить или убрать человека может
только сам автор. Кроме вкладок «Протокол» и «История» у протокола есть
«Вложения и комментарии» — файлы и обсуждение, как у актов: обязательный
комментарий возврата на доработку попадает в ту же ленту, а вложения
скачиваются только через проверяющую права вьюху; в архиве и то и другое
доступно для чтения, но не пополняется. Вкладка «Связанные мероприятия»
показывает реальные рабочие задачи, созданные по протоколу после полного
согласования (задачи согласования в неё не входят); задача, разбитая по
исполнителям, показана отдельной строкой на каждого. Для задачи протокола с
несколькими исполнителями доступна
галочка «Разбить задачу для участников»: по умолчанию она выключена и
согласованный протокол создаёт одну общую задачу на всех, а включённая — по
отдельной независимой задаче каждому исполнителю. На состав согласующих и на
официальный документ это не влияет: решение остаётся одним.

Согласующие считаются из участников «требуется согласование» и исполнителей
задач протокола за вычетом автора, каждому создаётся задача согласования со
сроком «+2 рабочих дня». Последнее согласование одной транзакцией архивирует
протокол и создаёт по одной реальной задаче на каждую задачу протокола;
протокол, который согласовывать некому, архивируется сразу при отправке.

Согласование протокола доступно из интерфейса. Автор отправляет протокол
кнопкой «Отправить на согласование» прямо из редактора: сохраняется и уходит
на согласование именно то содержимое, которое сейчас на экране, а модальное
окно предупреждает, что документ станет доступен только для чтения. На
странице протокола видно текущую редакцию, «Согласовано: X из Y», каждого
согласующего со снимком должности и подразделения, статус решения, дату и
время, а также причину, по которой согласование потребовалось. Согласующий
принимает решение здесь же — «Согласовать» (подтверждение в модальном окне,
комментарий не нужен) или «Вернуть на доработку» (обязательный комментарий);
возврат открывает протокол для правки, а повторная отправка создаёт новую
редакцию, при этом согласования прошлых редакций остаются видны в истории.

Готовый протокол выгружается как официальный документ: «Печать» открывает
печатную форму, «PDF» отдаёт тот же документ файлом. Обе кнопки рендерят одну
структуру и повторяют бумажный протокол предприятия — «Протокол», дата и
«№ N / тип» в одну строку, «Присутствовали», «Повестка», «Слушали», «Решили»
с ответственными и сроками, строки для подписей согласующих и «Подготовил». PDF собирается ReportLab (чистый Python, без
системных библиотек) шрифтом с кириллицей; путь к шрифту при необходимости
задаёт `PROTOCOL_PDF_FONT_PATH`, а его отсутствие в production ловит
`manage.py check`.

Задачи протоколов работают в общем разделе «Задачи»: реестр показывает «Тип
задачи» («По акту», «Согласование протокола», «По протоколу») отдельно от
статуса задачи, «Источник» ведёт на акт или на протокол, а поиск по источнику
находит и номер акта, и тип с номером протокола. Задача согласования — только
запись в очереди: она всегда открывает протокол и никогда не завершается
обычным «Завершить»; в архиве по ней виден настоящий исход (согласовано,
возвращено, отменено). Задача по протоколу остаётся обычной задачей с полным
циклом выполнения. Уведомлений, real-time-событий, печати и PDF для протоколов
пока нет.

**Документация.** Встроенная файловая система предприятия на `/documents/` с
двумя разделами. «Корпоративные документы» — дерево папок произвольной
вложенности с загрузкой, скачиванием и удалением: читают и скачивают все
авторизованные пользователи, создают папки и управляют файлами только
администраторы; начальные папки («Инструкции», «Служебные записки»,
«Нормативные документы», «Обучение», «Шаблоны») создаются миграцией.
Корпоративный документ — это версионируемая сущность: у каждого документа своя
страница с текущей версией, списком всех версий и историей. Загрузка нового
файла создаёт версию (v1 → v2 → v3), а не заменяет старую: прежние версии
остаются доступными для скачивания, администратор может вернуть любую из них в
статус текущей, а история пишет, кто и когда что загрузил. Версии есть только у
корпоративных документов.

«Вложения» — файлы актов, протоколов и задач, показанные ссылками на исходные
записи: у них нет версий и истории, их видно и можно скачать, но нельзя
загрузить, переименовать, заменить или удалить — ни пользователю, ни администратору. Файлы не копируются и
остаются там, где были загружены.

Поиск единый: строка поиска видна сразу при открытии раздела и ищет по
названиям корпоративных документов и папок и по вложениям — по имени файла, по
номеру акта или протокола и по описанию задачи. Результаты фильтруются
вкладками «Все / Корпоративные документы / Акты / Протоколы / Задачи» и
показываются одинаковыми карточками с расположением, датой и действиями;
системные вложения помечены как «Только чтение». На главной странице раздела
есть блок «Недавние документы» — последние загруженные файлы из обеих частей
библиотеки. Права доступа при поиске те же, что и при обычном просмотре.

**Готовность к эксплуатации.** Явный режим `APP_ENV`, проверки конфигурации
при старте, health и readiness endpoints, операционный журнал с `request_id`,
read-only команды проверки готовности.

## Стек

| Слой | Технология |
| --- | --- |
| Интерфейс | Django Templates + vanilla JavaScript, без сборщика и фреймворков |
| Приложение | Django, ASGI (Uvicorn) |
| База данных | PostgreSQL в production, SQLite в разработке |
| Real-time | Redis Pub/Sub → Server-Sent Events |
| Почта | корпоративный SMTP relay, отправка management-командой |

Точные версии — в `requirements.txt`. Полный список переменных окружения — в
`.env.example`. Celery, WebSocket/Channels, React и npm не используются.

## Архитектура

```
        браузер (Django Templates + vanilla JS)
          │ HTTP: страницы и фрагменты      │ EventSource: /realtime/events/
          ▼                                 ▼
   ┌────────────────────────────────────────────┐
   │            ASGI (Uvicorn) + Django         │
   │   views → permissions → services → models  │
   └──────┬──────────────┬──────────────┬───────┘
          │              │              │
     PostgreSQL        Redis        MEDIA_ROOT
   источник истины    Pub/Sub    protected media
                     best-effort
```

Приложения: `acts` (акты и workflow), `tasks` (задачи), `calculator`
(расчёт навивки и общий журнал «Проработка»), `notifications`
(уведомления и очередь писем), `realtime` (события, SSE, сверка),
`references` (справочники, только Django Admin), `accounts` (роли и
подразделения, вход/выход, управление — только Django Admin),
`maintenance` (технические команды), `ecosystem` (настройки, health,
логирование). Подробнее — в [docs/architecture.md](docs/architecture.md).

## Быстрый локальный запуск

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

python manage.py migrate
python manage.py seed_references
python manage.py createsuperuser
python manage.py runserver
```

По умолчанию используется SQLite; PostgreSQL, Redis и SMTP для локального
запуска не нужны.

Демонстрационные роли для разработки (в рабочей установке запрещены):

```powershell
python manage.py seed_demo_accounts --confirm-demo
python manage.py seed_demo_acts
```

Чтобы попробовать real-time, нужен ASGI-сервер и Redis — `runserver` работает
через WSGI и не удерживает SSE-поток:

```powershell
$env:REALTIME_ENABLED = "true"
$env:REALTIME_PUBLISHER_BACKEND = "realtime.backends.RedisRealtimePublisher"
python manage.py check_realtime_transport
python -m uvicorn ecosystem.asgi:application --reload --port 8000
```

Подробности, переменные и типовые локальные проблемы — в
[docs/development.md](docs/development.md).

## Проверки

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
python manage.py check_documentation
```

Дополнительно, только чтение: `check_logging`, `check_realtime_transport`,
`check_fresh_bootstrap`, `check_production_readiness`.

Production запускается только после успешных проверок:

```powershell
python manage.py check
python manage.py check_production_readiness
python -m uvicorn ecosystem.asgi:application
```

Тесты конкурентности пропускаются на SQLite, потому что `select_for_update()`
там ничего не делает; проверять блокировки нужно на PostgreSQL. Совместимость
с обоими бэкендами проверяет workflow `database-compatibility`.

## Направления развития

- разделение ролей PostgreSQL и переход из пилота в постоянную эксплуатацию;
- нагрузочная проверка real-time на реальном сервере и решение о persistent
  connections или пуле соединений по её результатам;
- цифровой ОТК и микро-MES как следующие предметные области — отдельными
  Django-приложениями;
- экспорт актов в PDF/Word (сейчас доступна только печать средствами браузера);
- «Входной контроль» как полноценный тип акта со своим набором правил.

Крупные компоненты — React, WebSocket/Channels, Celery, внешние платформы
логирования — добавляются только по отдельному архитектурному решению.
