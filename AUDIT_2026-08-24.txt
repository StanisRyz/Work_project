--------------------------------------------------------------------------------
КР-1. Отсутствует верхняя граница целых чисел -> переполнение integer
      в PostgreSQL. Проявляется ТОЛЬКО в production.
--------------------------------------------------------------------------------

Уровень:      Высокий
Расположение: plate_cutting/services.py:41-53  (функция _integer)
              plate_cutting/models.py:78-79    (plate_count, hole_count)
              templates/plate_cutting/page.html:77  (<input type="number">)
              static/js/plate_cutting.js:98    (регулярное выражение INTEGER)

Проблема:
  Функция _integer() проверяет только нижнюю границу (minimum) и не
  проверяет верхнюю. Поля plate_count и hole_count объявлены как
  PositiveIntegerField, что в PostgreSQL отображается в тип integer с
  максимумом 2 147 483 647.

  Ни одна из трёх линий защиты не ограничивает значение сверху:
    - HTML: <input type="number" min="1" step="1">  — атрибута max нет;
    - JS:   INTEGER = /^\d+$/                       — длина не ограничена;
    - Python: _integer(..., minimum)                — максимума нет.

Подтверждено экспериментально:
  POST /calculators/plate-cutting/presets/create/
  с телом {"name": "...", "packages": [{"range": "1",
                                        "plates": 9999999999999,
                                        "holes": 0}]}
  -> HTTP 201, значение 9999999999999 сохранено в базе (SQLite).

  На PostgreSQL тот же запрос вызывает
  psycopg.errors.NumericValueOutOfRange внутри bulk_create,
  транзакция откатывается, пользователь получает 500 и теряет набор.

Почему это важно:
  Это в точности тот класс дефектов, который невозможно воспроизвести
  при разработке: dev-окружение работает на SQLite (значение молча
  сохраняется), production — на PostgreSQL (запрос падает). Достаточно
  обычной опечатки на цифровой клавиатуре, чтобы получить 500.

Рекомендуемое исправление:
  1. Добавить параметр maximum в _integer() и передавать разумный
     предел (например, 2 000 000 000 технически или 1 000 000 пластин
     по бизнес-смыслу).
  2. Продублировать предел атрибутом max= у обоих <input>.
  3. Добавить CheckConstraint рядом с существующим
     plate_cutting_preset_package_plates_positive.

КР-2. Некорректный числовой ввод -> неперехваченный ValueError -> HTTP 500
--------------------------------------------------------------------------------

Уровень:      Высокий
Расположение: plate_cutting/services.py:48-50  (функция _integer)

Проблема:
  Предварительная проверка text.lstrip('-').isdigit() пропускает строки,
  которые затем не может разобрать int():

    '--5'  -> lstrip('-') = '5' -> isdigit() = True -> int('--5') = ValueError
    '²'    -> isdigit() = True                      -> int('²')   = ValueError

  Исключение не перехватывается ни в services.py, ни во view
  plate_cutting/views.py:preset_create, где обрабатывается только
  PlateCuttingValidationError.

Подтверждено экспериментально:
  POST /calculators/plate-cutting/presets/create/
  с "plates": "--5"
  -> ValueError: invalid literal for int() with base 10: '--5'
     поднимается из view (вместо ожидаемого 400 с русским сообщением).

Почему это важно:
  Весь контракт эндпоинта — «отклонить некорректный ввод тем сообщением,
  которое покажет модальное окно». Любой изменённый клиент, прокси,
  переписывающий тело запроса, или сформированный вручную запрос роняет
  эндпоинт в 500 и засоряет журнал ошибок.

Рекомендуемое исправление:
  Убрать предварительную проверку isdigit() (именно она и создала брешь)
  и обернуть само преобразование:

      try:
          number = int(text)
      except (TypeError, ValueError):
          raise PlateCuttingValidationError(f'{label}: введите целое число.')

  Исправлять вместе с КР-1 — это одна и та же функция.

СР-1. Незащищённое обращение к userprofile -> 500 при открытии редактора
--------------------------------------------------------------------------------

Расположение: protocols/forms.py:84

Проблема:
  Строка

      getattr(assignee.user.userprofile, 'department_id', '')

  защищает getattr'ом не то обращение. Само `assignee.user.userprofile`
  вычисляется первым и, если строки UserProfile нет, поднимает
  RelatedObjectDoesNotExist (наследник AttributeError и
  ObjectDoesNotExist). Значение по умолчанию у getattr при этом не
  срабатывает.

  Ситуация достижима: UserProfile может быть удалён в админке отдельно от
  User, а User защищён от удаления через PROTECT из
  ProtocolActionAssignee.

Последствие:
  Повторное открытие редактора протокола, в задаче которого назначен
  сотрудник без профиля, даёт 500.

Исправление:
  getattr(getattr(assignee.user, 'userprofile', None), 'department_id', '')

СР-2. Тихая потеря данных в редакторе протокола при смене подразделения
--------------------------------------------------------------------------------

Расположение: static/js/protocol_editor.js:73-88  (функция syncPair)

Проблема:
  syncPair() скрывает и отключает те <option> сотрудников, у которых
  data-department-id не совпадает с выбранным подразделением, и
  дополнительно выполняет:

      if (!available && option.selected) employee.value = '';

  Сохранённый участник (или исполнитель) попадает под это правило в двух
  реальных случаях:
    - сотрудник переведён в другое подразделение после сохранения
      черновика;
    - подразделение деактивировано (get_editor_directory() отдаёт только
      is_active=True), и соответствующего <option> в списке вообще нет.

Последствие:
  Строка перерисовывается пустой без какого-либо предупреждения, и
  следующее сохранение молча удаляет этого участника/исполнителя из
  протокола. Пользователь не получает ни ошибки, ни подсказки.

Исправление:
  Не очищать выбор автоматически. Показывать предупреждение у строки
  («сотрудник больше не относится к выбранному подразделению») и
  требовать явного действия автора.

СР-7. Количество исполнителей у задачи протокола ничем не ограничено
--------------------------------------------------------------------------------

Расположение: protocols/forms.py:330-338  (_getlist)
              protocols/forms.py:26        (MAX_ROWS = 60)

Проблема:
  MAX_ROWS ограничивает количество строк в каждом блоке, но не количество
  исполнителей внутри одной задачи: _getlist() читает все значения
  actions-<i>-assignees без ограничения.

Последствие:
  Один POST может создать (количество задач x количество активных
  сотрудников) строк ProtocolActionAssignee, а при отправке на
  согласование — столько же задач согласования и уведомлений, всё в одной
  транзакции. Дубликаты отсеиваются, поэтому предел — размер штата, но
  амплификация всё равно существенная.

Исправление:
  Ввести предел исполнителей на задачу (например, 20) в _clean_actions().

СР-8. Веерная рассылка realtime-событий протокола всем активным аккаунтам
--------------------------------------------------------------------------------

Расположение: realtime/recipients.py:127-140  (protocol_targets)

  Специального исправления сейчас не требуется. При росте штата —
  кэшировать справочник редактора и/или сузить аудиторию событий до

СР-9. Индекс search_name не используется поиском по подстроке

НЗ-1. Гонка поиска в модальном окне загрузки
      static/js/plate_cutting.js, wireLoadModal
      Обработчик клика по loadButton не вызывает
      window.clearTimeout(searchTimer). Отложенный на 250 мс поиск от
      предыдущего открытия может сработать после search('') и перерисовать
      список результатами запроса, которого уже нет в поле ввода.
      Механизм searchToken защищает только порядок ответов, но не этот
      случай.

НЗ-2. Расхождение RANGE_VALUE_MAX_LENGTH и миграции
      plate_cutting/constants.py:73, plate_cutting/migrations/0001_initial.py
      Константа вычисляется из диапазонов, но в миграции ширина колонки
      зафиксирована как max_length=4. Добавление диапазона с min_mm >= 10000
      потребует миграции, о которой легко забыть.

НЗ-3. Набор становится частично нерабочим при изменении диапазонов
      static/js/plate_cutting.js:200  (createPackage)
      Присвоение значения range, которого больше нет среди <option>, молча
      сбрасывает <select> в "". Пакет выпадает из итога, показывается
      только общий текст ошибки. Наборы хранят исходные данные именно для
      того, чтобы константы можно было менять — это единственное место,
      где обещание не выполняется.

НЗ-4. Значение из админки подставляется в заголовок Content-Disposition
      protocols/pdf.py:339-341  (protocol_pdf_filename)
      ProtocolType.code — свободный текст без валидатора — подставляется в
      имя файла без экранирования. Django блокирует CR/LF, но символы " или ;
      в коде типа нарушат кавычки в заголовке.

НЗ-5. Глобальная переменная регистрации шрифтов без синхронизации
      protocols/pdf.py:110-121  (_register_fonts)
      Флаг _fonts_registered — обычная модульная переменная. Под ASGI два
      одновременных первых запроса PDF могут выполнить регистрацию дважды.

НЗ-6. Отсутствие постраничной навигации
      protocols/selectors.py:build_protocol_list_state (и весь проект)
      Пагинации нет нигде — это общий для проекта подход, а не регрессия
      протоколов. Вкладка «Архив» будет расти неограниченно.

НЗ-7. Отсутствие квот и ограничения частоты
      plate_cutting/views.py:preset_create, protocols/views.py:protocol_create
      Ни квоты на пользователя, ни ограничения частоты запросов.

4.1. ПРОТОКОЛЫ — БИЗНЕС-ЛОГИКА

  Нумерация
    Выделение наименьшего свободного положительного номера под блокировкой
    строки select_for_update() по ProtocolType. Независимые серии номеров
    для каждого типа. Освобождение номера при удалении черновика.
    Ограничение unique_protocol_number_per_type как последний рубеж, а не
    как распределитель. Цикл allocate_protocol_number корректно
    обрабатывает пропуски в последовательности.

  Машина состояний
    Переходы DRAFT/REVISION -> APPROVAL -> ARCHIVED. Каждый переход
    перечитывает авторитетную строку ПОСЛЕ взятия блокировки и заново
    проверяет статус и действующее лицо. _finalize_protocol отказывается
    работать при наличии несогласованных позиций. Путь «согласующих нет»
    архивирует протокол в той же транзакции и публикует тот переход,
    который пользователь действительно наблюдает (DRAFT -> ARCHIVED).

  Редакции и повторное согласование
    Повторная отправка всегда открывает новую редакцию со своими строками
    ProtocolApproval. Предыдущие круги никогда не удаляются и никогда не
    засчитываются в текущий. Возврат оставляет решение возвращающего как
    RETURNED, остальные ожидающие переводит в CANCELLED, уже данные
    согласования сохраняются как APPROVED.

  Права доступа
    просмотр   — любой аутентифицированный (осознанное решение;
                 protocol_targets следует тому же правилу);
    изменение  — автор или администратор, только в статусах DRAFT/REVISION;
    удаление   — только автор, только черновик;
    отправка   — только автор (осознанно НЕ «автор или администратор»);
    решение    — только владелец PENDING-строки текущей редакции.
    Каждая проверка повторяется в сервисном слое под блокировкой строки,
    а не только в шаблоне. Скрытие кнопки нигде не является проверкой.

  Неизменяемость архива
    can_edit_protocol и can_delete_draft_protocol отвергают ARCHIVED,
    админка работает только на чтение (ReadOnlyAdminMixin), ProtocolAction
    защищён от удаления через PROTECT со стороны Task.protocol_action.

  Снимки данных
    display_name / position / department_name замораживаются у участников
    и у согласований и далее не следуют за профилем. _apply_participants
    корректно сохраняет уже существующие снимки и перезамораживает только
    изменившееся подразделение.

  Порядок удаления зависимых строк
    Выступления удаляются раньше участников везде, где это требуется, так
    что PROTECT у ProtocolSpeech.speaker никогда не срабатывает.

  Формула согласующих
    collect_required_approvers — единственное место, где формула
    существует. Дедупликация с сохранением обоих флагов, исключение автора
    и как участника, и как исполнителя задачи.

4.2. СВЯЗЬ С МОДУЛЕМ ЗАДАЧ

  Ограничение task_source_relations_match_source_type в базе, метод
  clean() с читаемыми сообщениями и связь один-к-одному
  Task.protocol_action делают невозможным создание второй задачи по одному
  решению протокола. can_complete_task отказывает для PROTOCOL_APPROVAL,
  то есть протокол нельзя согласовать через форму завершения задачи.
  task_detail перенаправляет задачу согласования на страницу протокола.
  Существующий функционал задач по актам не затронут.

4.3. ИСТОРИЯ И ДОКУМЕНТ

  Одно событие EDITED на одно реальное изменение (сравнение снимков
  документа до и после). Редакция записывается в каждом событии. actor
  через SET_NULL. Печатная форма и PDF рендерят одну и ту же структуру
  build_protocol_document(), поэтому разойтись не могут. Текст в PDF
  экранируется (xml.sax.saxutils.escape). Отсутствие reportlab или
  кириллического шрифта даёт контролируемый 503 и отдельную проверку в
  manage.py check.

4.4. ИНТЕГРАЦИЯ FRONTEND / BACKEND

  CSRF
    ensure_csrf_cookie на странице калькулятора, заголовок X-CSRFToken из
    cookie, @require_POST на пишущем эндпоинте, CSRF_COOKIE_HTTPONLY
    оставлен в False, чтобы токен был читаем. Формы протоколов используют
    {% csrf_token %}.

  XSS
    Не обнаружено. Список наборов строится через DOM-узлы и textContent.
    Единственный innerHTML в plate_cutting.js подставляет только
    отформатированные числа. Шаблоны экранируют по умолчанию, |safe и
    mark_safe в проверяемом коде отсутствуют.

  Live-фрагменты
    Только GET, перезагружают объект, заново проверяют request.user, не
    принимают пользовательских параметров, отдают
    Cache-Control: no-store и Vary: Cookie. Клиент не собирает URL из
    идентификатора — все адреса приходят из шаблона.

  Модальное окно подтверждения
    Подмена action у формы восстанавливается при закрытии диалога, поэтому
    «Сохранить черновик» не может остаться указывающим на эндпоинт
    отправки на согласование.

  Защита несохранённого ввода
    Редактор с несохранёнными данными никогда не заменяется live-обновлением;
    вместо этого показывается баннер конфликта и отключаются кнопки
    рабочего процесса.

  Согласованность параллельных списков исполнителей
    Списки actions-<i>-assignees и actions-<i>-assignee_departments
    сопоставляются позиционно. Отключённый (disabled) <select> не
    отправляется, из-за чего длины списков расходятся, и _clean_actions
    выдаёт контролируемую ошибку формы, а не смещение пар.
